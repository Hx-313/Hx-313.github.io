# 图像生成综合技能

本 Skill 统一调度图像生成相关能力，根据用户需求自动路由到对应的子能力模块。

## 能力边界声明（首轮强制）

本技能**仅覆盖以下 10 种图像生成/处理能力**（详见下文「能力概览」表）：背景消除、水印移除、SKU 换色、Logo 贴图、场景展示、细节生成、清晰度增强、模特图生成、图片翻译、指令绘图。

**越界信号 — 在调用任何 workctl 命令前先做范围自检：**

| 用户表达 | 正确处理 |
|---------|---------|
| 视频处理 / 视频剪辑 / 替换视频音频 / 给视频加字幕 / 视频翻译 | 不属于本技能；建议改用「商品视频生成」（alibaba-product-video-generation），或在视频后期工具人工处理 |
| 文档/PDF 内图片 OCR / 提取/识别 PDF 中的图 | 不属于本技能；建议先用 office-suite 解析文档拿到独立图片 URL，再让本技能处理 |
| 直接修改商品发布信息中的图片 / 替我替换主图并发布 | 本技能只生成图片素材；上架/替换图片请由「智能发品」或「商品信息优化」执行 |
| 创建系统级定时图片任务 / 自动每天生成 N 张 | 本技能仅支持单次会话内执行；定时素材任务请在卖家中心 → 智能营销中配置 |
| 多智能体编排（"@A 分析 → @B 生图 → @C 上架"） | 不假装编排；列出本插件实际能直接调用的 SubAgent 清单，请用户确认要执行哪一步 |
| 调用未在本技能 workctl 列表内的图像底层模型 | 列出 workctl 命令速查表中的可用 abilityCode，引导用户选择 |

**复合请求处理：** 用户一次请求中包含可做项 + 越界项时（例：去背景 + 改成视频），必须先完成可做项并 emit 凭证（图片 URL），再在末尾标注"本轮未处理项 + 建议路由"。

**对工具失败的负反馈处理：** 用户连续反馈"还是没生成 / 还是看不到图"时，禁止重复同一话术；下一步必须立即降级输出（i 豆余额提示 / 手动入口链接 / 已成功部分的清单）。

**意图误识别防护（高频问题）：**
- 用户附带图片并要求"分析/点评/看看这张图怎么样" → 这是图片审阅意图，不是生图请求。本技能**只在用户明确要求生成/处理/修改图片时才执行**，纯分析/点评/建议类请求应路由到其他技能或直接文本回答。
- 用户说"帮我写文案/写卖点/写标题" → 这是文案生成意图，不属于本技能。即使用户同时附带了图片，只要核心动作是"写文字"而非"处理图片"，应告知本技能仅处理图像并建议路由。
- 用户要求"批量生成 N 张不同商品的图" → 确认 i 豆余额充足后逐一执行，每张独立 emit 链接。若中途 i 豆耗尽，已生成部分正常交付，未完成部分标注原因。
- 用户在指令中附带图片作为"模板参考" → 必须确认是否要基于该图生成（如去背景/换色/场景图），还是仅作为风格参考。模糊时追问确认再执行。

**交付证据强化：**
- 每张已生成图片必须以可点击链接形式交付（Markdown 图片或 URL），禁止仅文字描述"已为您生成"
- 用户要求"无Logo"时，生成后必须自行校验图片描述中是否含 Logo/文字标志相关信息；若无法自行校验，在交付时主动提醒"请确认图中无 Logo，如不满意可重新生成"
- 批量任务逐项列出结果表格：序号 + 原图描述 + 生成结果（URL/失败原因）

## 通用执行规范

### workctl CLI 调用约定

- 通用生图命令：`workctl icbu product product-ai-image-generate --abilityCode <abilityCode> --imageUrl "<图片URL>" --prompt "<prompt>" --format json`
- 专用命令：SKU 换色用 `product-ai-image-color-change`，Logo 贴图用 `product-ai-image-custom-logo`，模特图用 `product-ai-image-model-generate`，图片翻译用 `product-ai-image-translate`；这些能力由命令路径固定，不额外传 `abilityCode`。
- 结果查询统一使用：`workctl icbu product product-ai-image-generate-result --requestKey "<requestKey>" --format json`
- 多张图片/多商品互不依赖时，优先生成 `workctl batch call` spec 并发提交或并发查询；每个 item 必须保留原图顺序、原图标识和 `requestKey` 映射。
- 当前图片生成结果查询是业务 `requestKey` 轮询：默认每 15 秒查一次，最多 8 次。如后续 schema 标记为 async，可优先改用 `--wait --poll-interval 15s --wait-timeout 120s` 或 `workctl task wait/status`。

### 参数校验（前置拦截）

**在调用任何 workctl 命令之前，必须先进行参数校验。如果必传参数为空或缺失，不得发起 workctl 请求，直接向用户返回明确的提示信息。**

#### 调用生成工具前校验

以下参数在调用对应 workctl 命令时为必传项，任一为空则**不发起请求**：

| 必传参数 | 校验规则 | 缺失时提示 |
|---------|---------|-----------|
| `abilityCode` / 专用命令路径 | 通用生图命令必须传对应 abilityCode；专用命令必须选择正确命令路径 | "系统参数异常，请重试" |
| `imageUrl` | 不能为空，必须是有效的图片 URL | "请提供需要处理的图片" |

**各能力额外必传参数：**

| 能力 | 额外必传参数 | 缺失时提示 |
|-----|------------|-----------|
| SKU换色 | `hexColor`（目标颜色） | "请提供目标颜色（如红色、#FF0000）" |
| Logo贴图 | `logoImageUrl`（Logo图） | "请提供需要贴合的 Logo 图片" |
| 场景展示 | `prompt`（场景描述） | "请描述您希望商品展示的场景" |
| 图片翻译 | `targetLang`（目标语言） | "请提供目标翻译语言（如英语、vi）" |
| 指令绘图 | `prompt`（用户指令） | "请描述您希望对图片进行的操作" |

#### 轮询结果前校验

生成工具调用成功后，检查返回的 `data` 字段（即 `requestKey`）：

| 必传参数 | 校验规则 | 缺失时提示 |
|---------|---------|-----------|
| `requestKey` | 不能为空，必须为生成工具返回的有效 `data` 值 | "图片处理任务提交失败，请重试" |

**校验逻辑：**
1. 在调用生成工具前，检查所有必传参数是否为空
2. 如果任一必传参数为空，**立即终止流程**，向用户返回对应的提示信息，引导用户补充缺失参数
3. 生成工具调用成功后、发起轮询前，检查返回的 `data` 字段（即 `requestKey`）是否为空
4. 如果 `requestKey` 为空，**不发起轮询请求**，向用户返回错误提示

### 输入处理

1. **图片输入**：接受图片URL或本地路径
2. **图片链接有效性校验**：
   - 在处理用户上传的图片前，需要校验图片链接是否可正常访问
   - 如果图片链接**无法打开、已失效、返回 404 或其他非正常状态**，**不发起任何 workctl 请求**，直接向用户返回以下固定文案：
   - **"您提供的图片链接无法访问或已失效，请重新上传图片或提供有效的图片链接"**
   - **批量场景**：如果用户上传多张图片，仅对链接失效的图片返回上述提示，链接有效的图片正常处理；需明确告知用户哪些图片链接失效
3. **参数提取**：从用户请求中提取必要的参数
4. **默认值**：对于可选参数使用合理的默认值
5. **批量处理时的图片去重与命名处理**：
   - **场景说明**：当用户上传多张图片进行批量处理时，可能存在图片命名相同（后缀不同）的情况
   - **处理流程**：
     1. **检测命名冲突**：按照"从左到右"顺序遍历所有输入图片，识别文件名相同（不含后缀）的图片组
     2. **判断内容一致性**：对于命名相同的图片，比对图片内容（如文件大小、图像哈希等）
     3. **去重处理**：
        - 如果图片内容完全一致，则视为重复图片，**只保留从左到右顺序中最靠前的那一张**
        - **边界情况**：如果去重后只剩1张图片，正常处理；如果所有图片都是重复的（理论上只保留1张），正常处理
        - **必须告知用户**：明确列出哪些图片被识别为重复并已去重
        - 示例输出：`"检测到重复图片：图片A.jpg 与 图片A.png 内容相同，已自动去重，只保留第一张"`
     4. **区分命名处理**：
        - 如果图片内容不一致，则对后续同名图片按序号区分命名
        - **命名规则**：基于"从左到右"顺序，**第一个出现的保留原名**，后续同名不同内容的按顺序添加 `_1`、`_2`、`_3`... 后缀
        - 示例：`product.jpg`（左起第1张）和 `product.png`（左起第2张）内容不同时，分别命名为 `product` 和 `product_1`
        - **必须告知用户**：明确告知用户哪些图片进行了重命名
        - 示例输出：`"检测到同名但内容不同的图片：product.jpg 保留原名，product.png 重命名为 product_1"`
   - **映射关系维护**：
     - **更新时机**：在调用 workctl 命令**之前**完成去重/重命名，并更新映射关系
     - 使用最终的命名（去重后的唯一图或重命名后的名称）作为图片标识
     - 确保requestKey与最终名称绑定，后续轮询和返回结果都使用最终名称

### 输出规范

1. **原样输出**：严格按照对应 references 文档中的输出格式输出，不要做任何额外处理
2. **错误处理与降级交付**：
   - 网络错误：自动重试一次。仍失败时，告知具体错误信息并提示用户检查网络后重试
   - 参数错误：提示检查输入参数，明确列出缺失或格式错误的字段
   - 服务错误：提示服务状态，建议稍后重试
   - **workctl 生成命令调用本身失败（非轮询阶段）**：自动重试一次；仍失败时，告知用户"图片处理服务暂时不可用"并建议稍后重试，同时返回已成功的其他图片结果（如有）
   - **轮询超时（8次/120秒仍未完成）**：必须向用户展示明确的超时消息，格式为"图片 [原图名称] 处理超时，任务 requestKey=[requestKey]，建议稍后重试"。禁止超时后静默跳过或只说"处理中"
   - **批量部分失败**：以表格形式展示每张图的处理结果，成功的展示图片 URL，失败/超时的展示原因。末尾汇总"共 N 张，M 张成功，K 张失败/超时"
3. **i豆不足错误处理**：
   - 当返回结果为 `{"errorCode":"30010004","errorMsg":"i豆不足","success":false,"data":null}` 时
   - 必须提醒用户：**"您当前生意助手的i豆不足，无法进行生图，请充值i豆后再进行使用"**
   - 同时返回已经执行完成的步骤获取到的结果（如有）
4. **requestKey 不合法错误处理**：
   - 当轮询结果返回 `errorCode: "20010003"`（错误信息含"requestKey不合法"）时，**立即停止该任务的轮询，不进行重试**
   - 向用户返回明确的失败提示：**"图片处理任务查询失败，任务标识无效（requestKey不合法），请重新提交图片处理请求"**
   - 批量/并行场景下，仅终止该 requestKey 对应的单个任务轮询，其他任务继续正常轮询；最终结果汇总时将该任务标记为失败并注明原因
4. **交付证据规则**：
   - `requestKey` 只代表图片处理任务已提交，不代表图片已生成；只有轮询到 `success=true`、`status=1` 且拿到非空图片 URL 时，才可以说"已生成/已处理完成"。
   - 用户明确要求数量、类别或版本（如 6 张主图、5 类共 10 张、每张白底图）时，必须先列出交付清单；最终返回前逐项核对，少一项就说"部分完成"并列出缺哪一张。
   - 批量图片必须按输入从左到右顺序返回，并标明每个结果对应的原图/类别；不能只给总链接或只说"全部完成"。
   - 用户反馈图片链接打不开或主体不对时，下一步必须先核验原链接/原图映射，再重试，不得直接口头确认成功。

### 注意事项

1. **超时处理**：
   - workctl 轮询：每15秒一次，最多8次

2. **结果验证**：
   - 检查 `success` 字段
   - 检查 `status` 字段（workctl服务）
   - 验证返回的URL有效性

## 组合使用

多个图片处理能力可以组合使用，支持串行、并行以及混合执行模式。

### 场景1：多张图片并行执行同一能力

**场景描述**：用户有多张图片需要执行相同的处理能力。

**示例**：批量去背景
- 用户上传N张商品图（如3张、5张、10张等），都需要去除背景
- **注**：实际执行时不限制图片数量，可以是任意多张

**图片顺序定义**：
- 用户上传的多张图片，按照**从左到右**的顺序排序
- 第1张图 = 最左边的图片，第2张图 = 左起第2张图片，以此类推
- **必须记录每张图片的原始顺序和对应的原图名称/标识**

**执行流程**（以3张图为例，实际可扩展到N张）：
1. **建立图片与任务的映射关系**（严格按照从左到右的顺序）：
   - 图片1（左起第1张）→ 调用 `workctl icbu product product-ai-image-generate`（abilityCode: imageExtraction）→ 获取 requestKey_1
   - 图片2（左起第2张）→ 调用 `workctl icbu product product-ai-image-generate`（abilityCode: imageExtraction）→ 获取 requestKey_2
   - 图片3（左起第3张）→ 调用 `workctl icbu product product-ai-image-generate`（abilityCode: imageExtraction）→ 获取 requestKey_3
   - ...（以此类推，每张图都有独立的requestKey）
   - **记录映射**：`{原图名称/标识: requestKey, 顺序: 1, 处理要求: xxx}`

2. **并行轮询获取结果**（每15秒检查一次每个任务的状态）：
   - 轮询 requestKey_1 → 获取图片1的处理结果
   - 轮询 requestKey_2 → 获取图片2的处理结果
   - 轮询 requestKey_3 → 获取图片3的处理结果
   - ...（轮询所有requestKey）

3. **严格一对一匹配结果**：
   - 图片1 对应 requestKey_1 的结果
   - 图片2 对应 requestKey_2 的结果
   - 图片3 对应 requestKey_3 的结果
   - ...（每张图对应自己的结果）

4. **等待所有任务都完成后，按输入顺序返回结果**
   - 结果顺序必须与输入图片顺序一致：结果1对应图片1，结果2对应图片2，以此类推

**重要**：
- **图片数量不限**：实际执行时可以是2张、3张、5张、10张或更多
- **图片顺序**：严格按照用户上传的从左到右顺序处理，第1张图是最左边的图片
- **必须维护输入图片与requestKey的严格映射关系**，确保结果不会错位
- **映射信息必须包含**：原图名称/标识、顺序位置、处理要求、requestKey
- 每个任务是独立的workctl 调用，有独立的requestKey
- 轮询时需要同时监控多个requestKey的状态
- **必须等所有任务都完成（status=1）后，再统一返回所有结果给用户**
- **返回结果时必须严格按照输入图片的顺序对应，不能混淆**：第1个结果必须是第1张图（最左边）的处理结果
- **原图名称/标识对应**：返回结果中必须明确标识对应的原图名称/标识，确保用户知道哪个结果对应哪张原图
- **标题与图片对应**：如果结果包含标题描述（如"红色T恤"），必须确保标题与实际图片内容一致，不能出现"绿色大衣"标题对应蓝色大衣图片的情况
- **失败重试**：如果某张图片处理失败需要重试，重新发起请求后会生成新的requestKey，**必须更新该图片与requestKey的映射关系**，确保最终返回结果时使用最新的requestKey

- **原图名称/标识对应**：返回结果中必须明确标识对应的原图名称/标识和处理能力，确保用户知道哪个结果对应哪张原图

### 场景3：一张图片执行多个能力（串行）

**场景描述**：一张图片需要按顺序执行多个处理能力，下一步依赖上一步的结果。

**示例流程**：去背景 → 场景展示
1. 先调用 `workctl icbu product product-ai-image-generate`（abilityCode: imageExtraction）生成白底图
2. **等待第1步完全完成后**，使用生成的白底图URL
3. 调用 `workctl icbu product product-ai-image-generate`（abilityCode: imageGenerate）将白底图合成到场景中
4. **等待第2步完全完成后**，返回最终结果

**示例流程**：换色 → 加Logo
1. 先调用 `workctl icbu product product-ai-image-color-change` 改变商品颜色
2. **等待第1步完全完成后**，使用生成的换色图URL
3. 调用 `workctl icbu product product-ai-image-custom-logo` 添加品牌Logo
4. **等待第2步完全完成后**，返回最终结果

**重要**：
- 串行执行必须**严格等待上一步完成**后再执行下一步
- 上一步的输出URL作为下一步的输入
- **必须等最后一步完成后，再返回最终结果**
- **i豆不足处理**：如果某一步返回i豆不足错误，返回上一步已成功生成的结果，并告知用户流程中断的位置（如"已完成换色，但在添加Logo时i豆不足"）

### 场景4：一张图片执行多个能力（串并行混合）

**场景描述**：一张图片需要执行多个能力，部分可以并行，部分需要串行。

**示例**：去背景后，同时进行【场景展示】和【清晰度增强】

**执行流程**：
1. 调用 `workctl icbu product product-ai-image-generate`（abilityCode: imageExtraction）去除背景
2. **等待去背景完全完成**，获取白底图URL
3. **并行执行**以下两个任务：
   - 调用 `workctl icbu product product-ai-image-generate`（abilityCode: imageGenerate）将白底图合成到场景
   - 调用 `workctl icbu product product-ai-image-generate`（abilityCode: imageHighDefinition）增强白底图清晰度
4. **等待两个并行任务都完成后，一起返回两个结果**

**重要**：
- 第一步必须串行完成，作为后续并行任务的输入
- 后续无依赖关系的任务可以并行执行
- **必须等所有并行任务都完成后，再统一返回结果**

### 通用执行原则

1. **任务映射管理（关键）**：
   - **必须建立并维护输入图片与requestKey的严格映射关系**
   - **图片顺序定义**：用户上传的多张图片按照**从左到右**的顺序排序，第1张图是最左边的图片
   - 使用字典或Map结构记录：`{原图名称/标识: requestKey, 顺序: 1, 处理要求: xxx}`
   - 轮询和返回结果时必须严格按映射关系对应，**绝对不能错位**

2. **workctl 调用**：
   - 每个任务都是独立的workctl 调用，有独立的requestKey
   - 记录每次调用的输入参数（原图名称/标识、处理要求）和返回的requestKey

3. **轮询机制**：
   - 串行任务：等待当前任务完成后再执行下一步
   - 并行任务：同时轮询多个requestKey的状态
   - 轮询时必须根据requestKey找到对应的输入图片（通过映射关系）

4. **结果返回**：
   - **无论串行还是并行，必须等所有任务都完成后，再统一返回结果给用户**
   - **必须按照输入图片的顺序返回结果**：第1张图（最左边）的结果在第1位，第2张图的结果在第2位，以此类推
   - 返回结果时必须明确标识每张输入图片对应的输出结果
   - **原图名称/标识对应**：返回结果中必须明确标识对应的原图名称/标识，确保用户知道哪个结果对应哪张原图
   - **严禁结果错位或混淆**
   - **标题与图片对应关系（关键）**：
     - 如果返回结果包含标题（如"绿色大衣"、"蓝色马克杯"），**必须确保标题与图片内容严格对应**
     - 示例：批量换色场景中，"绿色大衣"的标题必须对应绿色的大衣图片，不能对应其他颜色或其他商品
     - **验证方式**：返回前检查每个结果的标题描述是否与图片实际内容一致

5. **超时处理**：
   - 每个任务独立计算超时（每15秒一次，最多8次，最长120秒）
   - 某个任务超时不能影响其他任务的结果对应关系

6. **失败重试处理**：
   - 如果某个任务失败需要重新发起请求，**必须更新映射关系**
   - 重新调用 workctl 命令会生成新的requestKey，需要用新的requestKey替换旧的requestKey
   - **示例**：
     - 第1次调用：图片1 → requestKey_1（失败）
     - 重试调用：图片1 → requestKey_1_new（更新映射关系）
   - **必须确保**：重试后的新requestKey与原图名称/标识、顺序位置的映射关系正确更新
   - 返回结果时仍然按照原图顺序返回，但使用的是最新requestKey对应的结果

7. **i豆不足处理**：
   - 当某个任务返回 `errorCode: "30010004"`（i豆不足）时，**不进行重试**
   - 必须提醒用户：**"您当前生意助手的i豆不足，无法进行生图，请充值i豆后再进行使用"**
   - 同时返回已经执行完成的步骤获取到的结果：
     - **批量处理场景**：返回失败前已成功处理的图片结果，使用**去重/重命名后的最终名称**标识每张图片
     - **串行处理场景**：返回上一步已成功执行的结果，明确告知用户流程在哪一步因i豆不足中断
     - **并行处理场景**：返回其他已成功完成的任务结果，使用**去重/重命名后的最终名称**标识
   - 明确标识哪些图片因i豆不足未处理（使用最终名称标识）
