## Step 2 强制动作

无论是 `AI_SUGGEST` 还是 `USER_PROMPT` 场景，优化执行完毕后，**必须依次完成以下四个动作**，缺一不可：

### 强制动作 1：将优化结果写入 CSV 的 `after.*` 列并保存

- **写入前必须先解析表头行**：读取 CSV 第一行（表头行），通过列名动态定位每个 `after.*` 列的索引位置。**禁止按假设的列顺序或硬编码列序号写入**，必须用列名匹配索引
- 将每个商品的优化结果**按列名索引**逐字段写入对应的 `after.*` 列。`after.*` 列与 `before.*` 列的子字段名一一对应（如 `before.title` ↔ `after.title`），完整的对照关系见 `csv-schema.md`
- **⚠️ 写入前必须转义特殊字符**：将优化结果写入 `after.*` 列前，**必须按 `csv-schema.md` 中的"编码与分隔符"和"换行符编码规则"对字段值进行转义**。特别是 `description`、`properties`、`title` 等富文本字段，极易包含换行符（`\n`）、逗号（`,`）、双引号（`"`）等特殊字符。**处理顺序：① 将原始换行符替换为占位符（`\n` → `{{NL}}`、`\r` → `{{CR}}`）；② 将双引号转义为两个连续双引号（`"` → `""`）；③ 若字段值含逗号则用双引号包裹整个值**。未转义将导致 CSV 行断裂、列错位或解析报错，直接影响后续发布
- `before.*` 列保持不变（只读原始值），禁止修改
- 未优化的字段其 `after.*` 列保持空值
- **图片优化结果写入**：如果本次优化包含图片，`after.images` 的值来源于 `alibaba-global-ai-image-studio` Skill（通过 Sub Agent 唤起）的返回结果，而非批量优化工具。写入规则：用户指令为"优化图片"时**替换**原图片列表；用户指令为"生成图片"时**追加**到原图片列表末尾
- **写入时必须确保值写入正确的列索引**，避免列错位。写入后应校验：读取刚写入的行，检查 `after.*` 列名与值是否匹配
- **写入 `isPotentialCompetitive` 列**：从 `query_ggs_batch_optimize_result` 返回的每个 `ProductSandboxRecordDTO` 中读取 `isPotentialCompetitive` 字段（Boolean），写入 CSV 的 `isPotentialCompetitive` 列。该字段由后端自动填充，Agent **只读不写、不修改**
- **必须保存 CSV 文件**，确保后续 Step 3（发布）能读取到最新的优化结果
- 保存后向用户确认："已完成优化，共更新 X 个商品的 Y 个字段"

### 强制动作 2：查询商品质量分（PIS）并写入 CSV

> **⚠️ 质量分反幻觉硬约束（HARD RULE）**：质量分数值**只能**来自 `query_product_score` 工具的真实返回值 `data.finalScore`。以下行为均视为严重违规：
> - ❌ 在对话中口头预估分数（如"优化后预计质量分可以从 3 分提升到 5 分"、"预计能达到 5 分"）
> - ❌ 在预览中展示未经接口查询的分数
> - ❌ 在 CSV 的 `after.pis` 列写入硬编码数字或占位数值
> - ❌ 根据评分规则（`product-score-rules.md`）自行推算分数
> - ✅ **唯一合法做法**：调用 `query_product_score` → 从 `data.finalScore` 获取 → 写入 `after.pis` / 展示给用户
> - ✅ **未调用接口前**：对话中应说"优化完成后我会为您查询最新的质量分"，**绝不能给出任何具体数字**
>
> **⚠️ scoreDetails 反幻觉硬约束（HARD RULE）**：任何对 `scoreDetails` 字段的解读、归属判定、修复建议，**必须以 `tools-openapi.md` 中 `scoreDetails` 枚举说明表为唯一真相源**。
> - ❌ 禁止凭字段名望文生义（如把 `lead_time` 单独解读，而忽略文档定义里"满足7天"的判分阈值）
> - ❌ 禁止编造扣分项之间的联动关系（如"lead_time 与 shipping 联动判分"，文档未定义则不存在）
> - ❌ 禁止在文档未给出修复路径的情况下，自行推断修复方案
> - ✅ **必读再答**：每次解读 `scoreDetails` 之前，**必须重新 read 一次 `references/product-score-rules.md` 中的「scoreDetails 扣分项枚举说明」章节**（不依赖记忆），从中获取扣分项含义、A/B/C 分类及修复路径
> 
> **⚠️ 绝对强制：此步骤不可跳过！**
> 
> **⚠️ 豁免条件：当商品的 `generalProductId` 有值时（搬品/新发品场景），该商品尚未发布到国际站，不存在线上商品记录，调用 `query_product_score` 必定失败。此时必须跳过该商品的质量分查询，不写入 `after.pis`，预览中也不展示 PIS 信息。** 仅对 `generalProductId` 为空的存量商品执行质量分查询。
> 
> **如果不执行此步骤的后果**（仅针对存量商品）：
> - 用户无法看到优化前后的质量分变化
> - 无法判断优化是否真正提升了商品竞争力
> - 违反执行协议，可能导致发布失败
> 
> **验证方法**：在写入 CSV 后，对于 `generalProductId` 为空的存量商品，必须检查 `after.pis` 列是否有值。如果为空，说明质量分查询未执行，必须重新执行。`generalProductId` 有值的商品 `after.pis` 应保持为空。

- **对每个被优化的商品（`generalProductId` 为空的存量商品），逐个调用 `query_product_score` 工具**（**MCP 调用**）查询优化后的预期质量分
- **⚠️ Payload 工程化构造（HARD RULE）**：构造 `query_product_score` 请求参数时，**必须使用 `../scripts/build_product_score_payload.py` 脚本**，严禁手动拼接 JSON。执行流程如下：
  1. 运行 `python3 scripts/build_product_score_payload.py <csv_path> --row <行号>` 生成单商品 payload
  2. 捕获 stdout 输出的 JSON 作为 `query_product_score` 的请求体
  3. 直接调用 `query_product_score` 工具，传入脚本输出的 JSON（不得修改任何字段名或结构）
  4. 从返回值 `data.finalScore` 获取质量分并写入 CSV 的 `after.pis` 列（`before.pis` 列由圈品阶段系统填入，不可修改）

  脚本特性：
  - 固定读取 `after.*` 列，`after.*` 为空的字段不写入（后端自动补全）
  - `productId` 从 CSV 的 `productId` 列自动获取
  - 自动跳过 `isExcluded=true`、`generalProductId` 有值、`productId` 为空的商品
  - 自动处理 CSV 换行占位符解码、`priceType` 小写转换、废弃字段过滤等易错点
- 接口详情见 `tools-openapi.md` 中的 `query_product_score` 工具定义

### 强制动作 2.5：解读 scoreDetails 并向用户呈现剩余优化空间

> **⚠️ 此步骤为强制动作，不可跳过。无论用户是否指定目标分，每次 `query_product_score` 返回后必须执行。**

**执行流程：**

1. **必读文档（不允许凭记忆）**：每次执行本步骤前，**必须重新 read `references/product-score-rules.md` 中的「scoreDetails 扣分项枚举说明」章节**（包含扣分项含义、A/B/C 分类、对应 actions 字段及修复路径）。不允许凭字段名推断含义。

2. **列出所有扣分项**：从 `query_product_score` 返回的 `scoreDetails` 中，列出所有**值为 `true`** 的扣分项，按文档定义解读其含义与归属（基础分 / 加分项 → 哪一类）。

3. **强制分类**（依据 `product-score-rules.md` 中的扣分项对照表）：
   - **A 类 — Agent 字段层可处理项**：任何在 actions 枚举内的字段（`TITLE` / `PRICE` / `LEAD_TIME` / `MOQ` / `WEIGHT` / `DIMENSION` / `LOGISTICS_TEMPLATE` / `CATEGORY` / `DESCRIPTION` / `CPV` / `IMAGE` / `INVENTORY` / `KEYWORD`）
   - **B 类 — 需用户后台/线下操作项**：认证上传、定制能力开关、免费样品开关、运费计算器配置等不在 actions 枚举内的项
   - **C 类 — 不可干预项**：平台算法判定的项（如 `trend_product`），仅说明，不提供修复建议

4. **输出剩余优化空间表格**：在用户确认发布前，**必须以表格形式**输出剩余扣分项 + A/B/C 分类 + 各项可执行动作。表格格式示例：

   | 扣分项 | 含义 | 分类 | 可执行动作 |
   |--------|------|------|-----------|
   | `image_num` | 图片数量不足 | A 类 | 唤起 alibaba-global-ai-image-studio 补齐至 3 张 |
   | `lead_time` | 交期未满足 7 天 | A 类 | 调整首档交期 ≤ 7 天 |
   | `product_certification` | 缺少产品认证 | B 类 | 需用户在后台上传认证文件 |
   | `trend_product` | 非趋势品 | C 类 | 平台算法判定，不可干预 |

#### 迭代优化（当用户指定了目标质量分时）

**当用户指定了目标质量分（`targetScore`）时，在输出剩余优化空间表格后，还需执行以下迭代优化循环：**

1. **逐商品对比**：对每个被优化的商品，对比 `after.pis` 与 `targetScore`：
   - 如果 `after.pis >= targetScore`，该商品达标，无需进一步处理
   - 如果 `after.pis < targetScore`，该商品未达标，需要分析原因

2. **自动迭代优化**：对于 A 类（Agent 可处理）的扣分项，自动发起新一轮优化：
   - 根据 `product-score-rules.md` 对照表确定对应的 actions 字段和优化策略
   - 重新调用批量优化工具进行优化
   - 重新查询质量分，检查是否达标

3. **请求用户操作**：对于 B 类（需用户后台/线下操作）的扣分项，明确告知用户需要做什么：
   - 例如："商品缺少产品认证，需要您在后台上传认证文件"
   - 例如："商品未开启免费样品服务，需要您在后台开启"

4. **终止条件**：满足以下任一条件时停止迭代：
   - 所有商品均达标（`after.pis >= targetScore`）
   - 连续 3 轮优化无提升（分数未增加）
   - **已迭代 3 轮（达到最大迭代次数，硬限制不可突破）**
   - 剩余扣分项全部为 B 类或 C 类（Agent 无法处理）

5. **3 轮后仍未达标的处理（必须向用户说明）**：当达到 3 轮迭代上限仍有商品未达标时，Agent 必须**停止自动迭代**并向用户说明：
   - 当前已执行 3 轮自动优化，质量分从初始分提升到当前分
   - 剩余未解决的扣分项及其 A/B/C 分类
   - A 类剩余项：建议用户确认后手动指定优化方向，再发起新一轮优化
   - B 类剩余项：需要用户在后台手动操作（如上传认证、开启服务等）
   - C 类剩余项：平台算法判定，无法干预
   - **禁止**伪造结果或编造优化建议

> **⚠️ 重要**：迭代优化过程中，每次优化后都必须重新执行强制动作 1-4，确保数据一致性和预览准确性。

### 强制动作 3：生成并保存本地预览文件

> **⚠️ 重要区分**：
> - **对话框预览**：受限于对话框长度，最多展示前 10 个商品
> - **MD 文件内容**：必须包含**所有**优化过的商品，不得省略
> 
> **验证方法**：在输出对话框预览后，必须检查 MD 文件中的商品数量是否与 CSV 中的优化商品数量一致。如果不一致，说明 MD 文件不完整，必须重新生成。

- **必须在工作目录下创建实际的 CSV 数据文件和 MD 预览文件**
- **CSV 文件**：保存优化后的**完整** CSV 数据（**禁止截断**），文件名格式为 `optimization_result_<timestamp>.csv`。**无论原始数据量多大（如 500 个商品），都必须将 CSV 原封不动地完整写入本地文件，不得截断或只保留部分数据**
- **MD 预览文件**：将 Markdown 格式的 before/after 对比预览保存为独立文件，文件名格式为 `optimization_preview_<timestamp>.md`。**MD 文件必须包含所有优化过的商品，不得省略、截断或只保存部分数据**
- **MD 预览文件中必须包含 PIS 质量分展示**：在每个商品卡片的商品标识行下方，展示 PIS 分数变化（样式见 `optimize-preview-html.md` 中的 PIS 展示规则）。**豁免：`generalProductId` 有值的商品（搬品/新发品）不展示 PIS 信息**
- **文件必须实际写入磁盘**：不能仅在内存中处理，**必须在输出链接前确认文件已实际创建**
- **⚠️ 文件存在性验证**：在输出文件链接前，**必须验证文件是否已实际创建**。如果文件未创建，**禁止输出链接**，必须先创建文件再输出链接

> **⚠️ MD 渲染规范（必须严格遵循）**：生成 MD 预览文件和在对话中输出预览时，**必须严格按照 `optimize-preview-html.md` 中定义的渲染规则**来处理每个字段的展示。**禁止将 CSV 中的原始 JSON 字符串直接输出到 MD 中**——价格、交期、物流模板、属性、图片等复杂字段都有各自的特殊渲染规则（如价格需按阶梯价/区间价/SKU价/固定价分别渲染，物流模板需提取 `name` 字段，属性需逐个换行展示等）。渲染前必须先阅读并理解 `optimize-preview-html.md` 中的完整规范。

### 强制动作 4：输出 Markdown 格式的 before/after 对比预览并提供文件链接

- 基于刚更新的本地 CSV 中间产物，**立即在对话中输出** Markdown 格式的 before/after 对比预览
- **渲染逻辑必须严格遵循 `optimize-preview-html.md`**，包括页面结构、商品卡片布局、字段渲染规则（价格渲染规则、交期渲染规则、物流模板渲染规则、属性渲染规则等）、样式 Token、PIS 展示规则
- **仅展示实际有变化的商品**：仅展示 `after.*` 列中至少有一个字段非空**且与 `before.*` 对应字段值不同**的商品行。如果优化建议值与原值相同，或 `after.*` 为空，说明不需要优化，**不要给用户预览展示**
- 每个被优化的商品渲染为一张卡片，包含商品主图（`absSummImageUrl`）、商品标识（商品 ID + `before.title`，**商品 ID 渲染规则：当 `productId` 有值时优先渲染 `productId`，否则渲染 `generalProductId`**）、**PIS 质量分变化**（**豁免：`generalProductId` 有值的商品不展示 PIS**）、三列对比表格（`Field | Before | After`），差异字段用绿色高亮标记
- 可在 Markdown 中嵌入 HTML 标签（如 `<span>`、`<div>`、`<img>` 等）以实现样式效果（如绿色高亮、卡片布局）
- **对话框预览数量限制**：若商品数量较多（>10），在对话框中先展示前 10 个，提示用户"是否查看更多？"。**但 MD 文件必须包含所有优化过的商品，不得省略**
- **⚠️ 无优化结果时的处理**：如果所有商品都没有可优化的建议（即所有 `after.*` 列都为空或与 `before.*` 相同），**必须明确告知用户"没有可优化的建议，无需优化"**。**无论如何不可编造优化结果**，必须如实反馈
- **必须在对话结尾提供文件链接**：使用标准 Markdown 格式提供 CSV 和 MD 文件的下载或跳转链接
  - **链接格式必须为**：`[链接文本](文件名.md)`，**禁止使用 emoji 或其他非标准格式**
  - 示例：`[优化结果 CSV](optimization_result_20260402_143800.csv)`
  - 示例：`[优化预览](optimization_preview_20260402_143800.md)`
  - **⚠️ 禁止格式**：`📄 点击在线预览：商品基础质量优化预览.md`（这种格式无法正确渲染为可点击链接）
- **⚠️ 渲染后自检（必须执行）**：MD 预览输出完成后，Agent **必须立即回顾检查**刚输出的 Markdown 内容，确认是否存在格式乱码、HTML 标签未正确闭合、表格错位、转义字符显示异常（如 `&lt;`、`&amp;`、`\"` 等原始转义符直接暴露）等问题。若发现任何渲染异常，**必须立即重新生成并输出修正后的预览**，不要等用户反馈
- **⚠️ 格式稳定性要求**：MD 预览的格式**绝对不能乱码或发散样式**。必须严格按照 `optimize-preview-html.md` 中定义的渲染规则执行，确保 HTML 标签正确闭合、表格结构完整、样式一致。渲染完成后必须自检格式是否正确
- **⚠️ scoreDetails 解读自检（必须执行）**：在输出"剩余优化空间"表格前，Agent **必须自检**：刚才输出中是否所有 `scoreDetails` 的解读都引用了 `product-score-rules.md` 中的原文定义？如否，**必须重新 read `product-score-rules.md` 的「scoreDetails 扣分项枚举说明」章节后再输出**，不允许凭印象作答

> **执行顺序**：先完成动作 1（写入 CSV），再执行动作 2（查询质量分，**`generalProductId` 有值的商品跳过**），再执行动作 2.5（解读 scoreDetails 并输出剩余优化空间），然后执行动作 3（生成并保存本地文件），最后执行动作 4（输出预览并提供链接）。预览数据必须从已保存的 CSV 中读取，PIS 分数从内存中获取，确保预览内容与 CSV 及质量分一致。

## 可视化审阅

当用户查看预览后希望**在浏览器中直观审阅优化结果**，或需要**排除某些商品不参与发布**时，Agent 应主动告知用户可以启动可视化审阅页面：

> "如果您想在浏览器中直观查看每个商品的优化前后对比，并排除不需要的商品，我可以为您启动一个可视化审阅页面。需要我启动吗？"

### 功能说明

- **仅支持排除（删除）商品**：用户可以点击商品卡片上的「✕ Exclude」按钮将商品标记为排除，排除后该商品不参与后续发布
- **不支持编辑字段**：所有字段均为只读展示，如需修改字段值请通过对话告知 Agent
- **卡片式布局**：每个商品渲染为一张卡片，包含主图、商品 ID、标题、PIS 质量分、before/after 对比表格，样式与 MD 预览保持一致

### 启动流程

1. **启动审阅服务器**：运行 `csv-editor-server.py`，传入当前 CSV 文件路径
   ```bash
   python3 csv-editor-server.py <csv_file_path>
   ```
   使用 `launch-process`（`wait=false`）后台启动，服务器会自动选择可用端口并在浏览器中打开审阅页面

2. **用户在浏览器中审阅**：
   - 每个商品以卡片形式展示 before/after 对比，样式与 MD 预览一致
   - 用户点击「✕ Exclude」排除不需要的商品，点击「💾 Save Changes」保存排除操作（将 CSV 中对应行的 `isExcluded` 列设为 `true`）
   - 审阅器通过心跳机制保持连接，**浏览器关闭或 10 分钟无操作后服务器自动关闭**

3. **读取审阅结果**：用户保存并关闭审阅器后（通过 `read-process` 监听服务器输出确认），Agent 重新读取 CSV 文件，**重新执行 Step 2 的四个强制动作**（查询质量分 → 生成预览文件 → 输出预览），确保预览反映用户的排除操作

### 注意事项

- 审阅器仅监听 `127.0.0.1`（localhost），不暴露到外网
- 用户有未保存的排除操作时关闭浏览器，审阅器会弹出确认提示
- 服务器进程结束后，Agent 应使用 `kill-process` 确保进程已清理

## Step 3 发布或导出

### 存量模式（发布）

- **Input**：用户已完成双重确认（知悉风险 + 确认执行）
- **Action**：
  1. **筛选商品**：根据用户需求从本地 CSV 中间产物中筛选要发布的商品（如"发布前 20 个"、"发布所有优化过的商品"等）
  2. **分批调用发布接口**：将筛选出的商品按**每批最多 50 个**分批，每批内逐个调用 `alibaba-global-product-publish` Skill 的 `publish_ggs_migration_product` 接口发布（**MCP 调用**，每次调用只发布一个商品）。若商品总数超过 50，需拆分为多批依次处理，每批处理完毕后再处理下一批
  
     **传参规范**：
     - **编辑模式（存量品，productId 非空）**：`before` 传优化前完整快照，`after` 传优化后快照（未优化字段设 `null`）
  
  3. **⚠️ 同商品多类型优化合并规则（HARD RULE）**：当同一商品同时存在「字段优化结果」（来自批量优化任务，如标题、价格、交期等）和「图片优化结果」（来自 `alibaba-global-ai-image-studio` Sub Agent）时，**必须将两者合并到同一次 `publish_ggs_migration_product` 调用中一次性发布**。即 `after` 对象中同时包含优化后的字段值和优化后的图片列表。**严禁对同一商品分多次调用 `publish_ggs_migration_product`**，因为前一次发布会触发平台审核，导致后续发布被拒或覆盖前一次的优化结果。
  4. **汇总结果**：记录每个商品的发布状态（`SUCCESS` / `FAILED`），汇总成功和失败的数量，失败的商品需记录 `reason`（从返回的 `ProductSandboxRecordDTO.reason` 字段获取）
- **Output**：发布结果汇总

### 新发品模式（仅导出）

- **Action**：预览完成后，明确告知用户这些商品尚未上架，仅提供优化后的 CSV 导出。
- **Output**：提供 `[优化建议结果.csv]` 文件下载链接。
- **禁止调用**：严禁调用 `alibaba-global-product-publish` Skill 的 `publish_ggs_migration_product` 接口。

### Step 3 完成后的强制动作

> **以下三个强制动作缺一不可，每次发布操作完成后必须按 0 → 1 → 2 的顺序全部执行，任何一个都不能省略。**

#### 强制动作 0：同步发布状态至本地 CSV（最先执行）

- **每个商品发布完成后，立即将发布结果写回本地 CSV 中间产物**：
  - 发布成功：将该商品行的 `status` 列更新为 `SUCCESS`
  - 发布失败：将该商品行的 `status` 列更新为 `FAILED`，同时将 `reason` 列更新为失败原因（从返回的 `ProductSandboxRecordDTO.reason` 字段获取）
- **确保 CSV 文件实际写入磁盘并保存**，本地 CSV 必须始终反映商品的最新线上发布状态
- 已发布成功的商品（`status=SUCCESS`）在后续发布操作中应自动跳过，避免重复发布

#### 强制动作 1：生成并保存发布结果 MD 文件

- **必须在工作目录下创建发布结果 MD 文件**，文件名格式为 `publish_result_<timestamp>.md`
- 文件内容按照 `optimize-preview-html.md` 中的"发布结果渲染规则"渲染每个商品的发布状态
- 文件必须实际写入磁盘

#### 强制动作 2：在对话中直接展示发布结果 MD 预览并提供文件链接

- **必须在对话中直接渲染发布结果 MD 文件的完整内容**，让用户无需打开文件即可预览发布结果
- **在对话中输出发布结果汇总**（如 "X succeeded, Y failed" 或 "成功 X 个，失败 Y 个"，**必须使用用户当前使用的语言**）
- **逐个展示每个商品的发布状态**，按照 `optimize-preview-html.md` 中的"发布结果渲染规则"渲染
- **失败的商品必须展示失败原因**（`reason` 字段），让用户知道为什么失败
- **所有面向用户的文案（汇总、状态描述、提示语等）必须使用用户当前使用的语言**，参见 SKILL.md 中的「语言适配」
- **必须在对话结尾提供文件链接**，方便用户后续查看：
  - 示例：`[发布结果](publish_result_20260402_143800.md)`
- 发布成功后可按 `publish-result-file-reference.md` 输出结果卡片 JSON

> **⚠️ 每次发布操作完成后，必须将发布结果 MD 文件的内容直接展示在对话中，不能只给链接不展示内容。三个强制动作缺一不可。**
