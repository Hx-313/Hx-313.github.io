# 商品侵权风险检测（IP Infringement Risk Check）

> **版本 v1.0.0**

帮助跨境商家在商品上架前快速判断是否触碰平台知识产权红线。**仅检测阿里巴巴国际站（Alibaba.com）商品**，受理「阿里国际站商品链接 / 商品图片 / 纯文本」三类输入；对接 877 个平台高风险品牌黑名单，每条命中给出明确的合规优化建议（移除或调整为安全写法），并汇总成一段可直接执行的行动总结。

> 📎 **示例文件**：本 SKILL.md   只保留规则，所有举例（全证据表、命中表、报告三段式、合规建议写法等）统一存放在同目录 [examples.md](examples.md)。正文出现「示例见 examples.md §X」时去该文件对应小节查阅。

## 运行约束（最高优先级，每次执行都必须遵守）

### 约束 1：本技能不参与记忆系统（零记忆）

侵权检测属于**一次性合规审查**，每次检测的输入（商品链接 / 标题 / 图片）独立无关，没有"上一次怎么判"的延续价值；同时检测内容常含敏感商品信息，不宜留痕。因此：

- **不读取**任何商家画像、偏好、规则、历史检测记录；本技能执行不依赖任何历史上下文。
- **不写入**任何记忆文件：不向 `MEMORY.md` / `diary/` 追加内容、不调用记忆写入工具、不通过 `post_skill.py` 上报 `profile_updates` / `outcome` / `memory_query` 等任何字段。
- **若调度框架在执行前自动加载了 `bootstrap_load.py` 的返回值**：忽略其中的 `merchant_profile` / `user_preferences` / `learned_rules` / `memory` / `context` 字段，按"零上下文"执行检测。
- **若调度框架要求执行后调用 `post_skill.py`**：调用时所有可选字段全部省略或传空 JSON `{}`，仅满足框架最小调用约定。
- **会话级反思 / dream 整理一律跳过**，不为本技能产生任何持久化记录。

### 约束 2：报告必须在最终结果中完整展示（不得在思考过程中输出）

平台 UI 会把"工具调用之后才出现的文本"折叠到 think 块，导致用户看不到报告。因此本技能严格按两阶段执行：

- **阶段 1（静默执行，不输出任何用户可见文本）**：完成所有数据采集——alibaba.com 商品链接**只走 MCP `query_product_page_info` 直采**（MCP 不成功则直接回失败话术、终止，无任何降级抓取）/ 读取用户上传图片 / 调用匹配引擎 / 全证据表逐行判定 / 隐性售假扫描 / 补充扫描 / 整理命中清单。**这一阶段绝不向用户输出报告片段、表格行或任何中间结论。**
- **阶段 2（一次性连续输出最终报告）**：当且仅当阶段 1 全部完成、所有数据齐备后，**一次性、连续地、不被任何工具调用打断地**输出完整报告。报告输出过程中**不得再插入任何工具调用**——任何中途插入的工具调用都会导致后续报告内容被 UI 折叠到 think 块、对用户不可见。
- 若发现阶段 1 数据有遗漏，**必须先回到阶段 1 补齐**，再重新一次性输出报告，**不允许"先输出一半 → 调工具 → 续写"**。

## 何时使用

触发场景（即使用户没显式说"侵权"也要使用）：

- **明示**："这个商品有没有侵权风险？"、"帮我检测/扫描/排查商品侵权"、"查一下品牌风险"
- **隐含**：用户上传商品链接 + 询问"能不能上架"、"这款能卖吗"、"风险大不大"
- **图片审查**：用户上传商品图片询问"这张图有没有问题"、"这个 Logo 能用吗"
- **文案审查**：用户给出商品标题或详情文案，询问"这样写有问题吗"、"会不会被下架"

## 平台属性与 B2B 豁免规则（最高优先级，先于一切检测执行）

本技能服务的是**阿里巴巴国际站（Alibaba.com）B2B 跨境批发与定制贸易场景**，用户均为 B2B 商家，主要业务形态是**接受海外采购商的批发订单与 OEM/ODM 定制订单**。

在 B2B 语境下，部分文本表达是**正常的批发 / 定制业务用语**，并非售假信号；如果按零售（B2C）口径机械判断，会出现大量误判。因此，**在执行所有侵权检测之前，必须先做一轮"B2B 业务用语豁免预处理"**：

### 豁免触发词清单（B2B 同义词，命中即触发豁免）

| 类别 | 同义词（大小写不敏感、词边界匹配） |
|---|---|
| **批发类** | `wholesale` / `wholesales` / `bulk` / `bulk order` / `bulk purchase` / `MOQ` / `minimum order` / `B2B` / `trade` / `trader` / `distribution` / `distributor` / `reseller` / `批发` |
| **定制类** | `custom` / `customize` / `customized` / `customization` / `customizable` / `OEM` / `ODM` / `private label` / `make to order` / `MTO` / `tailored` / `bespoke` / `personalize` / `personalized` / `personalization` / `custom logo` / `custom design` / `custom packaging` / `your logo` / `your design` / `your brand` / `定制` / `订制` / `贴牌` |
| **样品 / 小批量类** | `sample` / `samples` / `sample order` / `trial order` / `small batch` |

### 豁免范围（精确边界，不得扩大化）

豁免**只针对"B2B 业务说明性文本"本身**，不豁免任何品牌侵权行为本身。具体边界如下：

**1. 豁免的范围（不纳入侵权判定）**

- 仅声明「批发 / 定制 / OEM / ODM」业务形态的整段文本片段，例如：
  - `MOQ: 500 pcs, OEM/ODM available, custom logo welcome`
  - `Wholesale price for bulk order, support customization`
  - `Sample order accepted, private label service`
- 这些片段中即使出现「品牌词」「Logo 字样」，但只要语义是**"我们能为你的品牌做代工 / 做你的私标"**，就不算 A1/A2/D2 命中。

**2. 不豁免的范围（仍按原规则判定，B2B 标签不构成挡箭牌）**

- 商品标题 / 详情中**直接使用他人品牌词**作为商品身份描述，即使周围有 wholesale / OEM 字样：
  - 反例：`Wholesale Nike Air Max sneakers, OEM accepted` —— `Nike Air Max` 仍是 A1 商标侵权，不豁免
  - 反例：`Custom LV pattern handbag, bulk order welcome` —— `LV pattern` 仍是 A1+B 双重侵权，不豁免
- 商品图片 / 详情图中**展示他人品牌 Logo / 立体商标 / 受版权保护的 IP 形象**，无论文本是否含 OEM / custom：
  - 反例：图中清晰展示 Nike 对勾 Logo，文本写 `OEM service available` —— 图片仍是 A2 命中，不豁免
- **D2 暗示售假关键词**（`1:1` / `replica` / `aaa` / `clone` / `yupoo` / `putian` / `thai version` 等）：即使搭配 wholesale，也仍判 D2 命中。理由：B2B 批发场景不需要也不应该用这些词描述商品。
- **配件类违规句式**（`canon battery` 缺主体）：即使写明 OEM，仍要按配件合规句式整改。
- **C 类外观设计专利侵权**（如复制 Apple AirPods 外观）：即使是 OEM 代工，专利权仍受保护，不豁免。

**3. 判定原则（一句话归纳）**

> 豁免的是「我们做批发 / 做定制」这件事的表达本身；不豁免「使用他人品牌作为商品卖点」这件事。
> 判断标准：把所有 B2B 同义词从原文中遮蔽后，剩下的文本是否仍构成侵权？是 → 不豁免；否 → 豁免。

### 豁免预处理操作步骤（每次检测必须执行）

在第 3 步「调用匹配引擎」与第 4 步「全证据表逐行判定」之前：

1. **标记豁免片段**：对入参文本（标题 + Attributes + Description + 卖点）按句号 / 换行切分，逐句扫描豁免触发词。命中触发词的句子标记为「B2B 豁免候选句」。
2. **二次甄别**：对每个豁免候选句，应用上方"不豁免的范围"逐条核验——若候选句同时包含高风险品牌词、Logo 字样、D2 暗示词、配件违规句式中的任意一项 → **取消豁免**，仍纳入检测。
3. **生效豁免**：通过二次甄别的句子从待检文本中剔除，仅剩余文本进入匹配引擎与 SOP 扫描。

**禁止在最终报告中暴露 B2B 豁免逻辑**：豁免预处理是技能的内部判断步骤，**最终报告中不得出现任何提示词、注释、说明行、脚注或元信息**来透露"已执行豁免"、"豁免了 N 段"、"wholesale / OEM 等已被识别为业务用语"等任何与豁免机制相关的内容。报告只输出最终的侵权判定结论，不解释推理过程。

## 核心数据资产

- **`assets/brand_blacklist.csv`** — 877 个平台知产高风险品牌（来自《品牌层_知产高风险知识库》，已清洗去重），含品牌名、内部品牌编号、权利人、投诉邮箱、权利类型、权利名/编号、管控大类、风险等级（S/A，**仅作内部存档字段，对外报告统一输出"高风险"，不得透出 S/A 字样**）。命中即视为高风险，不存在低风险条目。
- **`scripts/match_brands.py`** — 品牌匹配引擎，**四层渐进匹配**架构：
  - **L1 精确**：词边界匹配（不会让 "AC" 误中 "FACTORY"）、大小写不敏感、标点宽容（"Louis-Vuitton" 命中 "Louis Vuitton"）
  - **L2 Unicode 折叠**：自动处理重音字符（"Hermès" → "Hermes"、"Café" → "Cafe"）和全角字符（"ＮＩＫＥ" → "Nike"），无需在别名表里逐一登记
  - **L3 别名表**：`assets/brand_aliases.csv` 里的人工映射（如 `LV → Louis Vuitton`、`Hermès → Hermes`）
  - **L4 模糊匹配**：调用 RapidFuzz 滑窗扫描变形拼写（"Adidos" → "adidas"、"Loius Vuitton" → "Louis Vuitton"、"Niike" → "Nike"），用 ratio + token_sort_ratio 双指标 + Damerau-Levenshtein 编辑距离 ≤ 2 兜底，避免短常用词撞短品牌
  - **未引入向量匹配（embedding）**：变形词侵权的核心是"故意改 1-2 个字符"的字符级问题，而非语义问题；字符匹配在该场景下更精确、更可解释、且零外部依赖。详细理由见 `match_brands.py` 顶部 docstring。
- **`scripts/build_blacklist.py`** — 黑名单维护脚本。当用户提供新版 xlsx 时重新生成 CSV。
- **`scripts/test_matcher.py`** — 端到端冒烟测试，覆盖 L1 ~ L4 所有路径与误报回归（13 个用例，每次改动匹配引擎都应跑一次）。

## 审核 SOP 框架（侵权判定的核心依据）

本技能的判定标准与平台知产审核 SOP 完全对齐。无论入参是文本、链接还是图片，都必须按"四类违规 × 五类位置 × 三种特殊情况"这套框架逐项扫描；前提是 **品牌权利状态有效 且 商家未获得该品牌资质**。

### 四类违规（违规原因，必须全部覆盖）

| 类型 | 子类 / 判定要点 | 高发位置 | 举例 |
|---|---|---|---|
| **A. 商标侵权** | A1 文字商标 - 标准词：原样出现品牌词 | 文本、图片、视频 | 标题出现 `Nike`、`LV` |
| | A1 文字商标 - **变形词 / 近似词**：增减替换字母、打乱顺序、加空格 / 标点、拆分商标词，意图规避审核同时暗示品牌 | 文本、图片、视频 | `nik` / `nikey` / `niike` / `ni ke` 蹭 Nike；`lvs` / `L&V` 蹭 LV；`labobo` / `1abubu` 蹭 Labubu |
| | A1 文字商标 - **通用词获得显著性**：日常词汇在特定类目下成为品牌（"Apple" 用于电脑、"Amazon" 用于电商、"Coca-Cola"），需结合类目判断是否合理使用 | 文本 | 卖电脑配件用 `Apple` 字样、卖电商工具用 `Amazon` 字样 |
| | A2 Logo（图形 / 文字 / 图文结合）：图形商标、艺术化字体（如 `RB`、`LV` 字标） | **图片、视频为主** | Nike 对勾、Adidas 三条杠、LV 字母交叠 Logo |
| | A3 立体商标：商品形状或包装本身就是商标 | 图片、视频 | Hermès Kelly Bag 锁扣、Nike AJ1 鞋型、Dior 香水瓶、Cartier Tank 表盘、Cartier 钉子手镯 |
| **B. 著作权（版权）侵权** | 完全复制他人图片 / 视频；使用品牌或影视 IP 形象；他人美术作品作为商品 / 包装设计；抄袭外观 | 文本、图片、视频 | Naruto 忍者符号、Disney 角色、Stokke 椅子设计、ROMERO BRITTO 美术作品、小熊拖鞋外观 |
| **C. 外观设计专利侵权** | 整体形状 / 图案 / 色彩组合的相同或近似；从普通消费者视角看创新部分与显著特征 | **图片、视频为主** | Apple 耳机外观、Dyson 吹风机外观 |
| **D. 规避售假** | D1 图片规避：刻意遮挡 / 涂抹商标；白底图只展示型号词或品牌变形词；只画线条图 / 轮廓图；只展示包装或局部图，不直接展示商品 | 图片、视频 | 涂抹 Rhude 商标；丝巾遮挡 Chanel；不展示完整球衣；Nike / Adidas 球鞋线稿 |
| | D2 暗示售假（隐蔽售假）：价格明显不合理、暗示词汇、站外引流 | 文本、图片 | 见下方"暗示词检查清单" |

### 暗示售假关键词清单（D2 必查）

凡命中以下词汇或词汇组合（`+` 表示同时出现，不必相邻），即认定为暗示售假信号，列入"非高风险库品牌，但存在风险"：

`1:1` · `clone` · `replica` · `vip` · `3a` / `5a` / `7a` / `aaa` · `catalog`（联系商家获取清单暗示）· `whats` / `whatap`（拉线下）· `real + picture/photo/video` · `more + picture/photo` · `valid/real + serial` · `platform + restric` · `picture/photo + processed`（暗示图片处理过）· `luxury brand`（连写）· `luxury/famous/big + brand/design/designer` · `any/all brand` · `brand`（独立强调）· `clean + factory` · `putian`（莆田，假鞋）· `thai version/quality`（仿球衣）· `origin` / `ariginal`（拼写规避 original）· `yupoo`（图片网站）· `CC` / `CD` / `GG`（Chanel / Dior / Gucci 缩写）

### 五类违规位置（违规位置必查覆盖）

不要只看标题；命中可能藏在以下任何一个位置：

1. **商品文本** — 标题文本、属性文本、详情描述文本
2. **商品图片** — 主图（含原"轮播图"中所有商品图）、详情图
3. **视频 / 直播** — 商家有时把违规点专门放视频里规避自动审核，需逐帧检查；如检测对象是视频，需单独说明
4. **评论区买家图** — 买家带图评价中的图片侵权信号（针对该商品 Product Reviews，不是 Store Reviews）。**仅当输入 URL 形如 `https://www.alibaba.com/product-detail/...` 时启用**；只扫描图片，忽略评论文字。详细操作见下方 Step 1.6。

> **检测边界（重要）**：本检测**只看商品详情页 listing 本身**；店铺名 / 店铺头像 / 主营信息 / 店铺装修首页一律不获取、不检测（详见末尾"已知边界"）。

### 三种特殊情况

- **配件类合规表述**：发布"适用于品牌"的周边 / 配件，必须用 `for / compatible with / used for / replacement for / apply to / fit for + 品牌` 句式，并描述清楚配件本体是什么。
  - 错误：`canon battery`（缺主体）；正确：`battery for canon`
  - 错误：`phone case for apple phone case`（配件 for 配件，疑似规避）；正确：`phone case for apple`
- **二手商品**：表述规范、价格合理的二手品牌商品一般可售；但**奢侈品 / 高危品牌的二手仍受管控**，需要个案分析。
- **通用词类目相关性**：`Apple` 卖水果合理，卖电脑就是商标侵权；判断时必须看商品所在类目与品牌注册类目的相关性。

### 权利查询入口（推荐用户自查）

## 工作流

### 第 1 步：识别入参类型并提取可检测文本

> **入参范围闸门（最高优先级，先于一切采集动作执行）**：本技能**只检测阿里巴巴国际站（Alibaba.com）的商品**。受理的输入仅限三类：① **alibaba.com 商品链接**（形如 `https://www.alibaba.com/product-detail/...`）；② **商品图片**（用户上传或贴图片 URL）；③ **纯文本**（商品标题 / 详情 / 卖点文字）。**任何非 alibaba.com 国际站的商品链接**（1688.com、Amazon、Temu、SHEIN、AliExpress、Shopify / 独立站、淘宝 / 天猫等）**一律不受理**——直接按下方"非阿里链接拒绝话术"回复，请商家改提供阿里国际站商品链接或图片素材，**不要**对该链接做任何抓取 / 检测。

**入参分流：先判 URL 域名，再决定走向**

| 入参类型 | 处理动作 |
|---|---|
| **纯文本**（标题/详情段落/卖点） | 直接作为待检测文本 |
| **alibaba.com 商品链接**（形如 `https://www.alibaba.com/product-detail/...` 含数字 productId） | **唯一走 Step 1.0a「MCP 直采通道」**（直接调 `query_product_page_info`）。**这是阿里商品链接获取信息的唯一方式**；MCP 调用不成功则按 Step 1.0a 的"MCP 失败处理"直接回复说明话术，**不存在任何 web_fetch / 浏览器 / 脚本抓取的降级路径** |
| **非 alibaba.com 商品链接**（1688 / Amazon / Temu / SHEIN / AliExpress / 独立站 / 淘宝天猫 等任意非阿里国际站域名） | ❌ **不受理**：输出"非阿里链接拒绝话术"，请商家提供阿里国际站商品链接或图片素材。**不抓取、不检测该链接** |
| **商品图片**（用户上传或贴 URL） | 调用 `see_image` 让多模态模型读图，提取**所有可见品牌线索**——见下一节 |
| **混合**（图 + 文 + 链接同时出现） | 阿里链接 / 图片 / 纯文本照常并行处理并合并命中；其中**非阿里链接部分**按"非阿里链接拒绝话术"单独提示、不纳入检测，其余可检测内容正常出报告 |

**非阿里链接拒绝话术**（识别到非 alibaba.com 商品链接时，原样表达此意，语气友好简洁）：

> 抱歉，本侵权风险检测目前仅支持**阿里巴巴国际站（Alibaba.com）的商品**。您提供的链接不是阿里国际站商品链接，暂时无法检测。请改提供：① 阿里国际站商品链接（形如 `https://www.alibaba.com/product-detail/...`），或 ② 商品图片素材（主图 / 详情图截图），我即可为您做侵权风险检测。

- 若用户在拒绝后改提供了阿里链接 / 图片 / 文本，照常进入对应通道。
- 若一次输入里既有阿里链接（或图片 / 文本）又有非阿里链接：对可检测部分正常出报告，仅对非阿里链接附一句上述提示，不要因为含非阿里链接就拒绝整次检测。

##### Step 1.0a — alibaba.com 商品页：MCP 直采通道（**唯一通道，无降级**）

> **设计意图**：alibaba.com 商品页有官方的 `query_product_page_info` MCP（toolkit=alibaba, service=risk-for-accio），返回的就是平台风控视角的"该商品所有需要风险检测的信息维度"——含标题、主图（mainImageUrl + imageUrls 合并去重，统一归"商品主图"，**MCP 不区分"主图/轮播图"**）、属性（properties，**MCP 不返回 SKU 图与 SKU 名称**）、description（HTML 含详情文字与详情图）。该来源覆盖 100% 商家自有素材且**无反爬限制**，是平台官方风控数据源。
>
> **唯一通道铁律（强制）**：alibaba.com 商品链接获取商品信息**有且只有 MCP `query_product_page_info` 这一种方式**。**严禁**用 `web_fetch` 抓商品页、**严禁**用任何脚本 / 爬虫抓图、**严禁** `sessions_spawn(agent_id="browser")` 渲染商品页或任何浏览器抓取手段去获取该商品的标题/图片/属性/详情。**MCP 调用不成功时不存在任何降级抓取路径**——直接按下方"MCP 失败处理"回复说明话术、终止本次检测，**绝不**改用其它方式凑数据出报告。

**第 1 步：从 URL 提取 productId**

`https://www.alibaba.com/product-detail/<slug>_<productId>.html` —— productId 是 URL 最后一段 `_` 之后、`.html` 之前的纯数字串（长度通常 13 位）。如果用户直接给的是数字 productId，直接采用。

**第 2 步：调用 MCP —— 只调用一次，第一次就落盘（强制）**

> ⚠️ **MCP 每次调用都有成本与时延，严禁重复调用同一 productId。** 正确做法：**第一次调用就把完整 JSON 落盘到本地文件**，之后所有解析、转表、读取字段全部基于这个本地文件，**绝不二次调 MCP**。曾出现过对同一商品请求 3 次 MCP 的纯损耗，必须杜绝。

第一次调用并落盘。**严禁用 PowerShell 的 `>` 重定向 / `Out-File` 落盘**（它写 UTF-16 + BOM，会让下一步 JSON 解析直接报 `0xff in position 0`）。**必须用 Python 接管道写盘**（UTF-8 无 BOM），一条命令落盘 + 校验 success：

```bash
accio-mcp-cli call query_product_page_info --json '{"productId": <productId>}' 2>$null | py -X utf8 -c "import sys,os,json; raw=sys.stdin.read(); p=os.path.join(os.environ['TEMP'],'ip_check_<productId>.json'); open(p,'w',encoding='utf-8').write(raw); d=json.loads(raw); data=d.get('data') or {}; print('saved:',p); print('success:',d.get('success'),'| title:',data.get('title'),'| imgs:',len(data.get('imageUrls') or []),'| props:',len(data.get('properties') or []),'| desc_len:',len(data.get('description') or ''))"
```

返回顶层结构：`{"success":true, "errorCode":null, "errorMsg":null, "data":{...}}`（**以 `success` 字段判定成功，注意顶层无 `code` 字段**）；`data` 含 `title / mainImageUrl / imageUrls / properties / description / productId`。

落盘后所有后续步骤（转全证据表、读字段、see_image 取图 URL）**一律读 `%TEMP%\ip_check_<productId>.json` 这个本地文件**（Python 里用 `os.environ['TEMP']` 拼路径），不再调用 MCP。

**第 3 步：用辅助脚本一键转全证据表（读本地文件 + 落盘表格 + 用 read 查看）**

脚本默认 `print` 到控制台，但中文在 PowerShell（cp936）下会变 `??????` 乱码、根本读不了。**所以不要直接看脚本 stdout**——要么让脚本自己写文件，要么用 Python 接管道写盘（UTF-8 无 BOM）。**严禁用 `>` 重定向**（同样会带 BOM / 编码问题）：

```bash
py -X utf8 "<skill_dir>/scripts/mcp_to_evidence_table.py" --json-file "%TEMP%\ip_check_<productId>.json" 2>$null | py -X utf8 -c "import sys,os; raw=sys.stdin.read(); p=os.path.join(os.environ['TEMP'],'ip_check_<productId>_table.md'); open(p,'w',encoding='utf-8').write(raw); print('saved table:',p,'| lines:',len(raw.splitlines()))"
```

> 注：`--json-file` 路径在命令行里 `%TEMP%` 由 cmd 风格不展开，建议直接写绝对路径，或让脚本内部用 `os.environ` 取——最稳的做法是 Python 一次性拼好绝对路径传入。

落盘后**必须用 `read` 工具打开 `..._table.md` 查看全证据表与图片证据清单**（不要靠控制台 stdout，那里中文是乱码）。脚本输出一张完整的「商品全证据表」Markdown，**直接作为 Step 1.4.5 的产物使用**；后续重看直接 `read` 这个本地 md 文件即可，**不重跑脚本、更不重调 MCP**。

> 🛠️ **PowerShell 环境避坑模板（Windows，必须遵守，否则纯损耗 bash 调用）**：
> - **落盘一律用 Python 接管道写**（`命令 | py -X utf8 -c "import sys; open(path,'w',encoding='utf-8').write(sys.stdin.read())"`）。**严禁** PowerShell 的 `>` 重定向 / `Out-File`（默认写 UTF-16 + BOM，会让下一步 JSON 解析报 `0xff in position 0`，这是最高频的纯损耗坑）。
> - **严禁** `New-Object`（受限语言模式 ConstrainedLanguageMode 下不可用，会直接报错）；任何文件读写 / 编码转换 / JSON 解析**一律用 Python**（`py -X utf8 -c "..."`）。
> - **每条 `accio-mcp-cli` / 脚本命令都加 `2>$null`** 抑制 PowerShell 的 `#< CLIXML ...` 进度噪声（否则 stderr 会混入大段 XML 干扰判读）。
> - **中文输出别看控制台 stdout**（cp936 下变 `??????`）——脚本结果落盘成文件后用 `read` 工具查看。
> - **临时目录**：在 Python 里用 `os.environ['TEMP']` 拼绝对路径最稳；命令行里 `%TEMP%`（cmd 风格）和 `$env:TEMP`（PS 风格）在不同上下文展开行为不一致，不要混用裸变量。

> 📌 **脚本同时产出「图片证据清单」**（输出文末）：给每张图（主图 + 详情图）分配全局唯一编号 `IMG-01 / IMG-02 / …`，并附 `IMG↔URL` 对照表与可直接照抄的 see_image 输入数组(JSON)。**后续 see_image 调用、视觉发现标注、报告配图回填，全部以该清单为唯一锚点**，规则见 Step 1.4-IMG。务必完整读取脚本输出（含文末清单），不要只看证据表主体。

脚本完成的字段映射如下（与 Step 1.4.5 6 类信息严格对齐）：

| MCP 字段 | → 全证据表行 | 备注 |
|---|---|---|
| `data.title` | 商品标题（编号 `-`） | 原样保留 |
| `data.mainImageUrl` + `data.imageUrls`（**合并去重、保序**） | 商品主图（编号 `1` 起、可多张） | MCP 不区分"主图/轮播图"，全部归"商品主图"；mainImageUrl 通常重复出现在 imageUrls 中，必须按 URL 去重 |
| `data.properties[*]` | 商品属性（编号 `1` 起，格式 `attribute:<propertyText.defaultText>, value:<valueText.defaultText>`） | **`imageDTO` 字段一律忽略**（MCP 不提供独立的 SKU 图与 SKU 名称）；必须取 `defaultText` 字段（`allLocales` 仅是 Locale 元数据，不是真实文本） |
| `data.description` 剥 HTML 后的文字行 | 商品详情文字（编号 `1` 起，按 `<p>/<div>/<br>/<tr>/<li>` 切段） | 自动剥 `<style>/<script>`，HTML 实体还原 |
| `data.description` 内 `<img src>`（去重保序、协议补 `https:`） | 商品详情图片（编号 `1` 起） | 协议相对 URL `//sc04.alicdn.com/...` 必须补成 `https://...` |

**第 4 步：MCP 通道的硬约束**

| 条目 | 约束 |
|---|---|
| 评论区图 | **MCP 不返回评论区数据，全证据表对应行恒为 `（无）`，不采集不扫描**（详见 Step 1.6） |
| 商品视频 | 仍在第 5 步「补充扫描」处理（提醒用户自查 / 用户上传关键帧） |
| 店铺名 / 店铺头像 / 主营信息 / 店铺装修 | **不属于检测范围**，不获取、不检测 |
| 推荐位 / 卖家头像 | MCP 返回的字段不含推荐位（`Supplier's popular products` 等）、不含卖家头像 —— **天然规避**两大高频误判源 |
| 图片白名单 = 全证据表的 2 类图行 | 商品主图 / 商品详情图片，命中表的依据图 URL 必须 100% 取自这些行 |
| 第 2/4/4.6/5/6 步流程 | **完全不变**——MCP 通道产出全证据表后，下游品牌识别 / 逐行判定 / 隐性售假扫描 / 补充扫描 / 出报告全部照常走 |

**MCP 失败处理（唯一通道，无降级，直接回话术）**

阿里商品链接**只能**靠 MCP 拿数据，MCP 不成功就没有任何其它获取手段，因此**不出检测报告**，直接回复说明话术：

- 触发条件（任一即视为 MCP 调用不成功）：
  - MCP 返回 `success != true`（顶层 `success` 字段不为 `true`，或 `errorCode` / `errorMsg` 非空）或网络失败 / 超时 / 工具不可用
  - MCP 返回 `success:true` 但 `data` 缺失，或 `data.title` 与 `data.imageUrls` 同时为空（视为采集失败）
- 处理：**不**降级、**不**改用 web_fetch / probe / browser、**不**带空表出报告，直接回复下方话术并终止本次检测。

**MCP 失败说明话术**（原样表达此意，语气友好简洁）：

> 抱歉，本商品信息需要通过阿里巴巴国际站官方接口获取，当前接口暂时调用不成功（可能是接口繁忙或网络波动），暂时无法完成侵权风险检测。请稍后重试；如多次重试仍不成功，您也可以直接提供该商品的主图 / 详情图截图，我可以基于图片为您做检测。

- 用户改提供图片素材后，走"商品图片"输入通道照常检测。

#### 图片输入处理（仅用于"用户直接上传/粘贴商品图片"这一入参）

> **重要边界**：以下"图片归属校验 + 品牌识别"流程**只服务于"商品图片"入参**（用户主动上传截图或贴图片 URL）。**阿里商品链接的图片一律由 Step 1.0a 的 MCP 返回**（mainImageUrl + imageUrls + description 内嵌图），**绝不**用 `web_fetch` / 任何脚本爬虫 / browser 去抓阿里商品页的图。

##### Step 1.3 — 用 `see_image` 校验每张图的归属（图片输入场景）

把用户上传的图 URL 全部喂给 `see_image`（一次 ≤ 16 张，超过分批），逐张做形态一致性校验：

- **形态匹配**：图中商品的品类、款式、用途与商品标题 / 属性描述一致 → 保留
- **形态不匹配**：图中商品与标题描述完全不符（标题写"男士对折短款钱包"但图是"粉色女士单肩包"）→ 这必然是同店其它款 / 历史 listing 沉淀图 → 剔除
- **场景图 / 工艺图 / 对比图**：背景图、生产流程图、定制工艺展示图，可保留（它们是本商品的营销素材）
- **歧义处理**：无法 100% 确认归属 → **剔除而非纳入**，宁可漏检不可误判

##### Step 1.4 — 把所有保留的图统一过 `see_image` 做品牌识别

校验通过的所有图（含商品主图与 Description 详情图）一并进入第 2 步图片品牌识别，重点看：
- 商品主图通常 1000×1000 以上，**Logo / 印花 / 吊牌细节清晰**，是品牌识别的核心证据来源
- Description 详情图常包含**"inspired by"、品牌对比图、定制吊牌烫印工艺、防伪标位置**等关键证据
- 别忘了顶部那张主推图常带 ®/™ 符号或自有 logo 字样，这本身是合规信号但配合其它要素可能构成 D2

###### Step 1.4-IMG — 图片证据编号（IMG-NN）与 see_image 输入约定 🔒【强制·防配图错位】

> **背景（历史 bug 根因）**：曾出现"结论正确、配图 URL 错配（张冠李戴）"——根因是看图阶段（`see_image`）与写报告配图阶段之间，URL 靠**人肉回忆映射**，没有稳定锚点。本节用全局唯一编号 `IMG-NN` 作为唯一锚点，强制三处对齐：**MCP 图片顺序 == see_image 传入顺序 == IMG 编号顺序**。

**铁律（任一违反即视为证据无效，必须重做）**：

1. **唯一图源**：`mcp_to_evidence_table.py` 输出末尾的「图片证据清单」是本次检测**唯一**的图片 URL 来源。它给每张图（商品主图 + 商品详情图片，按 `[主图1..n, 详情图1..m]` 顺序）分配了全局唯一、连续的编号 `IMG-01 / IMG-02 / …`，并附带可照抄的 see_image 输入数组(JSON) 与 `IMG 编号 ↔ URL` 对照表。
   - 图片输入场景（用户直接上传/贴图）：同样按上传顺序给每张图编 `IMG-NN`，并自维护一份 `IMG→URL` 映射。

2. **see_image 必须照抄清单顺序**：调用 `see_image` 时，`image_paths` **必须直接复制**清单里的 "see_image 输入数组(JSON)"，**顺序不得改动、不得增删、不得替换为自己记的 URL**。如此第 k 张传入的图就**恒等于** `IMG-0k`。（超过 16 张分批时，按编号区间分批：第 1 批 IMG-01~16、第 2 批 IMG-17~…，批内仍保序。）

3. **看图描述必须带 IMG 编号**：视觉复核时，对每张图的发现**必须**显式写成 `IMG-NN → <这张图看到的内容/侵权信号>`，形成一份"视觉发现表"（内部维护）。因为传入顺序==编号顺序，第 k 张看到的就是 IMG-0k，不允许凭印象错位标注。
   - 示例：`IMG-07 → 盒侧标印 MFHP4AM/A / A3065 / Serial No.（伪造苹果料号）`；`IMG-06 → 盒背英/西双语照搬 AirPods 官方包装文案`。

4. **报告配图只写编号占位，URL 最后机械还原**：第 6 步写报告时，命中表/正文里的配图**必须先写成** `![描述](IMG-NN)` 占位符，引用的编号必须能在第 3 条的"视觉发现表"里找到对应描述。全文写完后，再用「图片证据清单」的 `IMG→URL` 映射把每个 `IMG-NN` **逐一机械替换**成真 URL。
   - **严禁**跳过编号、直接凭记忆手敲 alicdn URL。
   - 替换时若某个 `IMG-NN` 在映射表里查不到 → 说明编号写错或图不存在，**必须停下来核对**，不得猜测填一个 URL 充数。

5. **上传前自检（硬校验）**：报告 markdown 组装完成、上传语雀**之前**，逐条检查每个 `![](...)` 的 URL 是否都来自「图片证据清单」的 URL 列；任何一张配图 URL 不在清单内 = 配图错位嫌疑，必须回到第 3/4 条重新核对后再上传。

##### Step 1.4.5 — 构建「商品全证据表」（强制前置，所有侵权判断的唯一证据源）

> **设计意图**：之前版本只锁"图片白名单"，文字侧（标题/SKU 名/属性/详情文字）的命中证据没有结构化锚点，容易出现"凭印象引用、引用错位置、引用与原文不符"等问题。本步骤把图片白名单升级为**图文统一的全证据表**：所有可能承载侵权信号的元素（图 + 文字）必须先穷举进表，**第 4 步「全证据表逐行判定」就是以本表为唯一遍历主体来组装命中表，第 6 步报告里的每一条命中、每一个证据都必须能回溯到本表的某一行编号**——做不到的命中视为无效。

**强制要求**：必须**构建并在思考过程中维护一张完整的"商品全证据表"**（不输出给用户、仅作为内部锚点）。表格构建路径按入参类型分两条：

- **alibaba.com 商品链接**：由 Step 1.0a 的 `mcp_to_evidence_table.py` **一键产出**整张表，直接采用。本步骤的"取值规范"仅作为**校验清单**——对脚本输出做一遍 hash/数量自检，确认无字段缺失即可。
- **商品图片 / 纯文本入参**：基于用户上传的图片（经 Step 1.3/1.4 校验）与粘贴的文本，**按下方规范手动建表**（图片归"商品主图"、文本按标题/属性/详情切分）。

表格列：

| 列 | 含义 | 取值规范 |
|---|---|---|
| `信息类型` | 元素分类（封闭枚举，下面 6 类） | 见下方枚举 |
| `编号` | 该信息类型内部的序号 | 多元素类型从 `1` 起递增；单元素类型（如商品标题）统一写 `-` |
| `内容` | 文本片段 / 图片 URL / 属性键值对 | 文本原样摘取（不改写）；图片用完整 URL；属性写 `attribute:<key>, value:<value>` |

**信息类型 6 类封闭枚举**（顺序固定，缺哪类就标记 `（无）`，**不得新增类型**）：

| 信息类型 | 数据来源 | 编号规则 | 内容格式 |
|---|---|---|---|
| `商品标题` | MCP `data.title`（链接入参）／用户粘贴的标题文本 | `-` | 标题原文文本 |
| `商品主图` | MCP `mainImageUrl` + `imageUrls` 合并去重（链接入参）／用户上传的商品图 | `1` 起递增、可多张 | 完整图片 URL |
| `商品属性` | MCP `properties[*]`（链接入参）／用户粘贴的属性文本 | `1` 起递增 | `attribute:<key>, value:<value>` |
| `商品详情文字` | MCP `description` 剥 HTML 后切段（链接入参）／用户粘贴的详情文本 | `1` 起递增（按段落 / 卖点条目分） | 段落 / 卖点原文文本 |
| `商品详情图片` | MCP `description` 内 `<img src>`（链接入参）／用户上传的详情图 | `1` 起递增 | 完整图片 URL |
| `商品的买家评论图片` | **MCP 不返回评论区，本行恒为 `（无）`**（无任何其它抓取通道补全） | `1` 起递增 | 完整图片 URL |

> 各信息类型实际填表样子见 [examples.md](examples.md) §1 全证据表（内部表格）示例。

> **历史名称对齐**（避免历史 prompt / 报告口径串位）：原 9 类中的 `商品轮播图` 已并入 `商品主图`；`商品 SKU 图` 与 `商品 SKU 名称` 因 MCP 不提供已**彻底废弃**——**绝不**再以这三个名称建表、不再在命中表里出现，也不再用"商品主图取编号 0"这种旧约定。`商品的买家评论图片`：因阿里商品只走 MCP、MCP 不返回评论区，此行**恒为 `（无）`**。

**内部表格示例**（思考过程里维护，不输出给用户；用 markdown 表格存储以便引用）：见 [examples.md](examples.md) §1 全证据表（内部表格）示例。

**填表硬约束**（违反则全证据表无效，必须重建）：

1. **图片侧来源闭锁**：`商品主图` / `商品详情图片` 的 URL 必须 100% 来自 MCP 返回（链接入参）或用户上传图片（图片入参）。**绝不**凭印象编造 URL。MCP 返回的字段天然不含推荐位 / 平台 UI / 卖家头像，无需额外过滤。
2. **文字侧原样摘取**：标题、属性、详情文字必须从 MCP 原字段（链接入参）或用户粘贴文本（文本入参）**原样摘取**，不改写、不翻译、不缩短。属性必须用 `attribute:<key>, value:<value>` 标准格式；多个属性逐行列出。
3. **完整性**：文字部分按"段落 / 条目"颗粒度全量列出，**不**跳过看似"无关"的内容（侵权信号常藏在卖点小字、Brand Name 字段里）。
4. **去重**：同一行内容重复出现仅保留 1 条；不同信息类型即使内容重复也必须各自列一行（如主图与详情图同 URL，要列两次，分别归类）。
5. **缺类标记**：某类信息确实不存在时（如评论图恒为无）保留行头并写 `（无）`，不得直接删行——否则后续无法判断"是没有"还是"漏抓"。

**数据缺失处理**：阿里商品链接的全证据表完全来自 MCP；如果 MCP 返回的标题 / 图片同时为空，按 Step 1.0a「MCP 失败处理」直接回话术，**不**用 web_fetch / browser 等任何其它方式补数据，**不**带空表出报告。

##### Step 1.5 — 图片证据来源闸口

> **MCP 通道**：alibaba.com 商品链接走 Step 1.0a 后，可用于命中举证的图 = `mcp_to_evidence_table.py` 输出全证据表中 `商品主图 / 商品详情图片` 2 类行的并集。MCP 字段天然不含推荐位 / 平台 UI / 卖家头像，无需额外过滤。
> **图片入参**：可用于举证的图 = 用户上传、经 Step 1.3/1.4 校验保留的图。

**写入命中表（第 2 列"侵权内容"依据图）的所有 `![](URL)`，URL 必须 100% 来自全证据表的 `商品主图` / `商品详情图片` 行**（即必须能在全证据表里找到对应行）。

绝对禁止的来源：
1. 你在思考 / 调试过程中临时贴在上下文里的任何 URL（包括上一轮对话出现过、其它 listing 的图、网页其它区块的图）
2. 任何不在全证据表内、由你"凭印象"或"补充"写出的图片 URL

##### Step 1.6 — 评论区买家图（**不采集、不扫描**）

阿里商品只走 MCP，而 `query_product_page_info` **不返回评论区数据**，且**没有任何降级抓取通道**去补全评论区。因此全证据表「商品的买家评论图片」行**恒为 `（无）`**，本步骤**不执行任何扫描**。

#### 命中举证范围约束（强制遵守）

> MCP 返回的字段天然只含本商品的标题 / 主图 / 属性 / 详情，**不含**以下推荐位 / 平台 UI 区块——故本约束在 MCP 通道下基本是冗余的防御层。**图片入参**场景下，若用户上传的截图里混入了这些区块，仍按本约束排除。

**必须排除**以下区块的所有文字与图片，不得纳入侵权检测对象：

| 区块类别 | 必须排除的区块名（中英文标识词） |
|---|---|
| alibaba.com 推荐位 | `Other recommendations` · `Recommended for you` · `You may also like` · `Customers also viewed` · `Customers who viewed this also viewed` · `Frequently bought together` · `Often bought with` · `Bundle and save` · **`Supplier's popular products`** · `More from this supplier` · `More from this seller` · `Hot selling in this category` · `Related items` · `Top picks` · `Sponsored products` · `Ranking` |
| 通用 | 店铺导航栏 / 页脚 / 广告横幅 / 第三方 banner / 平台促销活动模块 |
| 评论区文字 / 评论区图片 | 一律不作为侵权依据（见 Step 1.6）。 |

#### 图片形态一致性校验（强制操作步骤）

MCP 返回的图已天然限定为本商品的主图与详情图（不含推荐位 / 平台 UI / 卖家头像）。即便如此，仍需用 `see_image` 做形态一致性校验，避免把"商家自己塞进详情图里的同店其它款拼图"误算到本 listing：

1. **用 `see_image` 验证商品形态一致**：把每张图过 `see_image`，确认图中商品形态、品类与商品标题 / 属性描述**严格一致**。例：标题是 `Men's Bifold Short Wallet`，但某张图是粉色女士单肩包 → 必定是同店其它款拼图，**立即剔除**，不纳入检测。
2. **属性栏交叉验证**：商品属性中的 `Color / Size / Style / Material / Pattern Type` 字段描述应能匹配图片。某张图的颜色 / 款式 / 图案与属性声明都对不上 → 必定不是本商品图。
3. **歧义处理**：当某张图是否属于本商品**无法 100% 确认**时，**剔除而非纳入**——宁可漏检，不可误判。

判断依据总结：**"标题描述的商品 + 图中真实呈现的商品" 必须严格一一对应**。任何形态不一致、品类不一致、款式明显是同店其它款的图都必须剔除。如有歧义，宁可漏检也不要错把同店其它款混入 —— 否则会把无关品牌的命中算到本商品头上，导致误判。

#### 已知误判教训（务必参考）

**同店其它款被当成本商品图（Baellerry D9168 钱包案例，2026-04）**：listing 标题为 `Men's Bifold Short Wallet`，但商家在详情图里塞了粉色 Miu Miu 风格单肩包、棕色 LV 老花链条包等同店其它款拼图。若不严格区分图片归属，会把这些同店款当成本商品款式图，错误命中 LV、Miu Miu 两个高风险品牌。**正确做法**：发现某图是粉色女包 / 棕色印花链条包，与"男士对折短款钱包"标题完全不符 → 立即判定为同店其它款 → 剔除，不纳入命中表（如商家全店其它 listing 售卖这些抄款，在第三段"行动总结"中提示"建议全店自查同款"，而非把命中算到本 listing 头上）。

**报告依据图来源错误（2026-05 高频 bug）**：写命中表时，依据图位置的 `![](URL)` 必须 100% 来自全证据表 `商品主图` / `商品详情图片` 行。**正确做法**：写表前对每张依据图 URL 做一次"是否在全证据表内"的核验；不在表内的一律换成表内同主题图，或直接剔除该行命中——绝不允许凭印象贴一个不在证据表内的 URL。

**卖家头像 / 公司 Logo 不属于商品（2026-05 教训）**：阿里页面常混入卖家公司头像、客服 IM 头像、公司 Logo 等卖家身份图，它们本身可能含品牌联想，但**不属于商品本身**，与"商品是否侵权"无关。MCP 通道返回的字段天然不含这些卖家身份图——若在图片入参场景遇到此类图，**不得**作为商品命中依据；如对卖家身份本身有合规疑问，在第三段「行动总结」里单独提示"店铺主体身份建议核查"，而非污染商品命中表。

### 第 2 步：图片中的品牌识别（含遮挡推测）—— 核心能力

商家常见规避手段：用马赛克、贴纸、模糊、裁剪等方式遮挡 Logo，企图绕过自动检测。**你必须能"猜"出被遮挡的品牌**——这是本技能区别于普通 OCR 的关键价值。

调用 `see_image` 时，明确让多模态模型回答以下问题（在 prompt 中列出）：

1. 图片中**直接可见**的品牌文字、Logo、商标符号？
2. 是否有被**马赛克/模糊/贴纸/色块/裁剪**遮挡的区域？如果有，根据以下线索推测背后可能是什么品牌：
   - **商品形态**：球鞋的鞋型（AJ1/Yeezy/Air Force）、包款轮廓（LV Speedy/Hermès Birkin/Chanel Flap）、手表设计语言（Rolex Submariner 表盘、AP Royal Oak 八角）
   - **配色与图案**：Burberry 格纹、LV Monogram 棕色花纹、Gucci 红绿条纹、Hermès 橙色、Tiffany 蓝
   - **字体残留**：被马赛克部分遮挡仍能看到的字母轮廓、字体风格（衬线/无衬线/手写）
   - **构图与场景**：奢侈品包装盒（Tiffany 蓝盒、Cartier 红盒、Hermès 橙盒）、专卖店货架、品牌广告海报样式
   - **吊牌/水洗标/防伪标**：即便文字模糊，标签布局也可能暴露品牌（Supreme 红色 box logo 形状、LV 防伪烫印位置）
3. 商品类目是什么（鞋/包/服装/电子产品/化妆品等）？
4. 输出一个"**疑似品牌候选清单**"，每个候选附**置信度（高/中/低）**和**判断依据**。

把所有"直接可见"和"疑似遮挡"的品牌名汇总成一段文本，喂给 `match_brands.py`。

**说明置信度的重要性**：低置信度的"猜测"也要列出，让用户自己判断是否风险——但在最终报告里区分"确认命中"和"疑似命中"两类。

### 第 3 步：调用匹配引擎，构建「品牌候选池」（仅作判定字典，不直接组装命中行）

**关键约束**：本步骤的输出**不**直接成为命中表的行。匹配引擎只负责告诉你"有哪些品牌词在采集到的全部文本里出现过、出现在文本的哪些片段里"——它无法告诉你这个品牌词出现在**全证据表的哪一行**、对应的**位置**是商品标题还是商品详情文字、对应的**图片依据**是哪一张。组装命中表是第 4 步「全证据表逐行判定」的职责。

操作：把第 1、2 步收集到的所有文本（原始文案 + 图片识别结果）拼成一段，运行：

```bash
py "<skill_dir>/scripts/match_brands.py" --text "<拼接后的文本>"
```

或者写到临时文件用 `--file` 传入。引擎返回 JSON，含每个命中的：品牌名、原文位置、上下文片段、权利人、投诉邮箱、风险等级等。

**输出 JSON 关键字段**（每个命中项）：

| 字段 | 说明 | 用法 |
|---|---|---|
| `brand_name` | 命中的高风险品牌名 | 第二部分命中表「侵权品牌」列直接用 |
| `matched_substring` | 文本中实际命中的原文片段 | 第二部分命中表「侵权内容」单元格的「依据」段直接用 |
| `match_method` | 命中路径：`exact` / `exact_normalized` / `alias` / `fuzzy` | 内部追溯，无需写入报告；`fuzzy` 命中可在合规建议里强调"疑似变形词，必须移除" |
| `match_score` | 匹配分数 0–100；L1/L2/L3 恒为 100，L4 为 RapidFuzz 实际分 | 内部参考，无需写入报告 |
| `alias_of` | 若走别名路径，记录原始别名（如命中 `Hermes` 但用户写的是 `Hermès`） | 内部参考 |
| `rights_owner` / `complaint_email` / `rights_type` / `risk_level` | 权利人 / 投诉邮箱 / 权利类型 / 平台风险等级 | 风险等级仅作内部分级，对外口径仍按"高/中风险"两档输出 |

**输出 JSON 全局字段**：

| 字段 | 说明 |
|---|---|
| `fuzzy_enabled` | L4 模糊匹配是否启用（true 表示 RapidFuzz 已加载） |
| `fuzzy_threshold` | L4 阈值（默认 90） |
| `blacklist_size` / `alias_count` | 当前加载的高风险品牌条数与别名条数 |

**CLI 可选参数**：

- `--no-fuzzy` — 禁用 L4 模糊匹配（仅跑 L1/L2/L3）。当文本极短或想严控误报时使用。
- `--fuzzy-threshold <0-100>` — 调整 L4 RapidFuzz 阈值，默认 90。降低阈值会增加召回但也会增加误报，不建议低于 85。
- `--blacklist <path>` / `--aliases <path>` — 指定自定义黑名单/别名 CSV。

**RapidFuzz 未安装时的降级行为**：自动跳过 L4，`fuzzy_enabled` 标记为 false，L1/L2/L3 仍正常工作；不报错、不阻塞流程。如需启用 L4，运行 `py -m pip install rapidfuzz`（已写入 `assets/requirements.txt`）。

**匹配引擎能力边界**：四层匹配覆盖了"标准词命中 + 重音/全角折叠 + 别名映射 + 字符级变形拼写"。**仍不能识别 Logo、外观抄袭、暗示售假关键词组合、配件违规句式、IP 形象著作权** —— 这些必须靠第 4 步的「全证据表逐行判定」结合图片识别结果与 SOP 框架补齐。

匹配引擎产出的全部 hits（每个含 `brand_name` + `matched_substring` + `match_method` + `rights_owner`）暂存为「品牌候选池」，进入第 4 步使用——**这些 hits 不直接写进命中表**，必须经过第 4 步的逐行判定才能成为正式命中。

### 第 4 步：全证据表逐行判定（命中表的唯一构造来源）

> **设计原则**：命中表里的每一行必须**先有依据，再有判定**——而不是"先想到品牌，再去找一张图当依据"。本步骤通过强制以全证据表为遍历主体，把"判定动作"和"证据来源"绑定到同一行，从根本上杜绝"图文不符 / 凭印象命中 / 错挂位置"的幻觉。

#### 第 4 步执行流程（必须严格按行枚举，不得跳过）

**Step 4.1 — 准备遍历集合**

把 Step 1.4.5 全证据表的所有非空行（即排除标记为 `（无）` 的行）按以下顺序展平成一个有序列表：

```
[商品标题, 商品属性#1..N, 商品详情文字#1..N,
 商品主图#1..N, 商品详情图片#1..N]
```

文字行在前、图片行在后只是为了减少视觉切换成本，**判定本身是逐行独立的、与顺序无关**。（`商品的买家评论图片` 恒为 `（无）`，不进入遍历集合。）

**Step 4.2 — 对每一行执行 5 类判定**

对列表里的**每一行**（无论文字行还是图片行）依次问以下 5 个问题，**只看本行的 `内容` 列、不看其它行、不调用任何"印象"**：

| # | 判定项 | 适用 | 怎么判 |
|---|---|---|---|
| **a** | 高风险品牌命中 | 文字行 + 图片行（图片走 see_image 识别结果） | 本行内容里有没有任何字符串落在第 3 步「品牌候选池」里？文字行直接做子串比对；图片行看该图的 `see_image` 识别结果列表里有没有候选品牌 |
| **b** | 高风险库外 IP / 著作权 | 文字行 + 图片行 | 本行内容里有没有 Disney/Pokemon/Marvel/Naruto 等影视动漫美术 IP？图片行同样看 `see_image` 识别结果（包括"疑似遮挡推测"的候选） |
| **c** | 变形词 / 谐音 / 通用词蹭品牌 | 仅文字行 | 本行文字去掉空格 / 标点 / 数字后，是否近似某个高风险品牌（覆盖匹配引擎 L4 的盲区，如 `ni ke` / `1abubu`）？通用词（Apple / Tiger 等）出现时检查类目相关性 |
| **d** | D2 暗示售假关键词 | 仅文字行（标题 / 属性 / SKU 名 / 详情文字） | 本行是否含 `1:1` / `replica` / `aaa` / `mirror` / `clone` / `dupe` / `yupoo` / `putian` / `thai version` 等词？**B2B 豁免对 D2 无效**，即使本行同时含 wholesale / OEM / custom 仍判命中 |
| **e** | 图片规避手法 / 配件违规句式 | 图片行用 `e1`，文字行用 `e2` | `e1`：本行图片是否有马赛克 / 涂抹 / 贴纸 / 色块遮挡商标，或仅展示线条图 / 局部 / 包装而非完整商品？`e2`：本行文字是否为品牌配件违规句式（缺 `for/compatible with/replacement for` 前缀，如 `canon battery`） |

**Step 4.3 — 命中即成行，未命中即跳过**

- **命中**任何一项 → 立刻按下表格式生成一条命中表记录，**不缓存、不延迟、不与其它行合并**：

  | 字段 | 取值 |
  |---|---|
  | 风险等级 | 高风险品牌（a/b 命中且品牌在 `assets/brand_blacklist.csv` 中）→ `🔴 高风险`；其它 SOP 信号 → `🟡 中风险` |
  | 侵权位置（第 2 列上半段） | **就是当前遍历到的这一行的"信息类型"**——不允许跨行借位置 |
  | 侵权依据（第 2 列下半段） | **就是当前遍历到的这一行的"内容"**——文字行原样摘取 5–10 词上下文，图片行用 `![](URL)` 嵌入这一行的 URL（**不允许换图**） |
  | 侵权品牌（第 3 列） | a/b 命中写品牌名；c/d/e 写信号特征 |
  | 合规建议（第 4 列） | 一句话动作描述 |

- **未命中**所有 5 项 → 在内部清单中将该行标记为 `OK`，**不进入命中表**。

**Step 4.4 — 自检清单（出报告前必跑）**

聚合 Step 4.3 产出的所有命中行后、生成第 6 步报告前，**逐行自检**：

- [ ] 每行的"位置"是否真的来自当前遍历到的全证据表行（不是"商品主图"位置但贴的图却是某张详情图）？
- [ ] 每行的"依据图 URL"是否真的与该行"内容"列的 URL 完全一致（不是同 hash 不同尺寸）？
- [ ] 每行的"依据文本片段"是否真的是该行"内容"列的子串？
- [ ] 每行的"侵权品牌"是否能在该行依据本身（文本子串 / 图片 see_image 结果）里找到证据？

**任何一项不符合，立即删除该行重判定。**做不到逐项自检通过的命中，宁可不出。

#### 已知失败模式（必须避免）

| 失败模式 | 表现 | 根因 | 防御策略 |
|---|---|---|---|
| **凭印象命中** | 报告写"商品涉及 Nike"，但全证据表所有文字行都没出现 Nike，所有图片行 see_image 也没识别到 Nike | LLM 对商品类目（如运动鞋）做了类目级联想，没基于实际证据 | Step 4.2 严格按行 + Step 4.4 第 4 项自检 |
| **图文错位** | 命中写"商品主图含 LV Logo"，但贴的依据图实际是某张商品详情图 | LLM 在写报告时随手挑了一张"看起来比较显眼"的图 | Step 4.3 强制位置 = 当前遍历行 + Step 4.4 第 1 项自检 |
| **依据图与品牌无关** | 命中写"含皮卡丘形象"，但贴的依据图实际只是一张商品白底图，see_image 没识别到任何 IP 形象 | LLM 用了"风险描述对的、举证错的"路径 | Step 4.4 第 4 项自检 + 第 6 步报告生成的"依据图必须自身承载侵权信号"约束 |
| **跨行合并** | 把多张不同位置的命中合并到一行，位置写"商品主图 / 商品详情图片"但只贴了一张图 | LLM 想"压缩报告" | Step 4.3 命中即成行、不合并；只有同一行内容确实横跨多个位置（同一图既是主图又被复用为详情图）时才允许 ` / ` 拼接位置 |

### 第 4.6 步：隐性售假场景扫描（在第 4 步逐行判定之后执行，命中并入命中表）

> **设计意图**：第 3、4 步主要靠"明文品牌词 / 可见 Logo / 立体商标 / D2 关键词"识别侵权，但有一类售假**刻意不出现明文品牌**——通过去标仿版瓶型、批量货架陈列、整箱堆积、手绘/渲染替代实拍、品牌名压黑条、站外引流广告等手法规避识别，实质指向知名品牌仿冒品。这类"隐性售假"会被前面流程漏判，必须用本步骤补扫。

**执行前置**：本步骤**运行时必须先读取**技能目录下的 [`concealed_fake_sales_standard.md`](concealed_fake_sales_standard.md)，以该文件的"通用识别维度（CF-G1~G7）+ 品类细分标准（CF-香水-1~9 / CF-护肤-10~13）+ 文字暗示词清单"为**唯一判定依据**，不得凭记忆自行发挥。

**执行流程**：

1. **判适用性**：先看商品类目。属于**香水 / 护肤 / 彩妆等美妆个护品牌敏感品类**（标准的实拍背书集中于此）→ 必做；属于箱包 / 鞋服 / 手表 / 配饰等品牌敏感品类 → 参照"通用识别维度"做，但指认从谨慎；属于纯工业品 / 原材料 / 无品牌敏感度功能品**且无站外引流/暗示词** → 可快速跳过本步骤。
2. **图片侧逐行比对**：对全证据表 `商品主图` / `商品详情图片` 每一行，结合该行 `see_image` 视觉发现，比对标准文件的 CF-G1~G7 与品类细分标准——重点看：信息缺失（不展示品牌/型号/净含量）、品牌标识处理（遮挡/涂抹/打码/压黑条）、仿冒外观（去标但瓶型盒型高度仿大牌）、批量暗示（货架整排/整箱堆积/大量散样，注意阈值）、规避实拍（手绘/渲染/AI/截图替代主图）。
3. **文字侧扫描暗示词**：对全证据表 `商品标题` / `商品属性` / `商品详情文字` 每一行，扫描标准文件"文字暗示词清单"（`original` / `original sign` / `原单` / `hot selling` / `catalogs` / `contact us` / `warehouse` / `whatsapp` / `现货仓` 等）。
4. **命中成行**：命中任一标准 → 按 Step 4.3 同一格式在命中表新增一行。**档位分两种**：
   - **🔴 高风险例外（CF-G8 明示 1:1 仿冒）**：若命中标准文件第二·五节 CF-明仿-G8——即图文**同时**出现「知名品牌产品型号/系列名列举」**与**「`1:1 product` / `1:1 clone` / `1:1 copy` / `1:1 replica` 等明示按正品仿制的措辞」→ 这已是**公开声明售卖仿品**，档位判 **🔴 高风险**（不是隐性规避，不降级成 🟡）。"侵权品牌列"写被仿冒品牌（型号已点明可指认到品牌，如 `Nike（1:1 仿冒 Air Force 1）`）；"合规建议列"写 `移除：全文知名品牌型号列举与 1:1 product / 1:1 clone 等仿制措辞，并下架该仿冒商品`。
   - **🟡 中风险（其它隐性售假）**：命中第二/三节其它（非 CF-G8）标准 → 档位 **🟡 中风险**：
     - **位置**：取自命中所在全证据表行（遵守"位置=遍历行、依据=本行内容"约束）。
     - **侵权品牌列**：写**信号特征**（如 `隐性售假（无标香水货架批量陈列）`、`隐性售假（品牌名压黑条+Original 暗示词）`、`隐性售假（站外引流 Contact Us 广告图）`），除非画面/文字已明确对应某高风险品牌，否则**不强行指认具体品牌**。
     - **合规建议列**：按"移除 / 调整为"句式给出（如 `移除：批量货架陈列图与去标仿版瓶身图，改用单品正面实拍并完整标注品牌授权/型号/净含量`）。
5. **去重（关键）**：若同一证据已在第 3/4 步被识别为明确高风险品牌（🔴 高风险），**不再重复出隐性售假行**；本步骤只补"常规品牌匹配漏掉、但手法明显指向售假"的情形。
6. **追溯硬约束**：隐性售假命中同样受全证据表追溯约束——依据图 URL 必须来自全证据表 `商品主图` / `商品详情图片` 行、依据文字必须是全证据表对应行子串；找不到来源行的命中视为无效，必须删除。

> 隐性售假命中归入第 6 步命中表，与第 4 步产出的命中**合并排序**（排序规则见第 6 步"表格行排序规则"）。本步骤不单独出表、不在报告中暴露"隐性售假标准"文件名或扫描机制，只呈现最终命中结论。

### 第 5 步：补充扫描（仅查全证据表外的风险，不直接组装命中行）

第 4 步只能判定全证据表内的 6 类内容。还有 1 类风险**不在全证据表内**，必须在本步骤单独提醒用户自查（**不**进入命中表，写在最终报告"行动总结"末尾或单独的"补充提醒"段）：

1. **商品视频 / 直播**：本检测无法逐帧识别视频内容（MCP 返回的字段不含视频内容）。如商品含视频，提醒用户人工抽查关键帧。如用户主动上传关键帧截图，可按第 4 步同样规则判定，命中行的"位置"写 `商品视频`，依据末尾用 `（来源：用户上传截图）` 注明。

> **店铺级内容**：店铺名 / 头像 / 主营 / 装修不检测、不进命中表；如用户有合规疑虑，在"补充提醒"段提示自查即可。

### 第 6 步：按三段式模板生成报告

无论是否命中、无论入参类型，**始终按这个结构输出**：

## 输出模板（必须严格遵守）

````markdown

## 一、商品基本信息

> 用**中文一段话**简介：这是什么商品、关键参数、目标市场。**全段 ≤ 150 字符**（按中文字符计，1 个汉字 = 1 字符，1 个英文字母 = 1 字符）。品牌名、型号、规格参数等可保留英文原文（如 XORUS ASTURIE 110, 110mm/15g）。**严禁使用表格、列表、分行**，必须是单段流畅文字。

## 二、侵权风险判定

> **第一行必须给出明确判定**，加粗显示，三选一：
> - **存在高风险侵权**（命中 N 项管控名单品牌：xxx、yyy）
> - **存在中风险侵权**（未命中管控名单，但发现 M 项需警惕的品牌词/关键词/图片细节：zzz）

如果存在风险（含高风险品牌命中或潜在风险），必须附一张**命中表**。**表格采用固定四列表头，列名、列顺序、列含义不得修改**：

| 列号 | 列名 | 含义 | 取值规范 |
|---|---|---|---|
| 1 | **风险等级** | 风险严重程度（仅两档） | 只允许两种取值，必须带固定 emoji 前缀：`🔴 高风险` / `🟡 中风险`。emoji 与文字之间用一个半角空格分隔。判定口径见下方"风险等级判定口径"。**禁止**使用 S/A、严重/警告、高/中/低三档、其它颜色圆点（🟢🔵）、其它 emoji（🚨⚠️❗）、纯文字（不带 emoji）等任何其它写法 |
| 2 | **侵权内容** | 命中依据本身（含位置 + 依据） | **单元格内必须分两段**：第一段写侵权位置（`商品标题` / `商品主图` / `商品属性` / `商品详情文字` / `商品详情图片` / `商品视频`），用 `<br>` 换行；第二段写实际依据（文本片段或真实图片）。详见下方"第 2 列填写规范" |

#### 风险等级判定口径（仅两档）

- **高风险**：满足以下任一条件即归为高风险——
  - ① 命中 `assets/brand_blacklist.csv`（877 个平台知产高风险品牌，含原 S/A 两级）中的任意条目（**不再区分 S 与 A 两档**，对外统一口径"高风险"）；
  - ② **明示 1:1 仿冒（CF-G8）**：商品图文**同时**出现「知名品牌产品型号/系列名列举」与「`1:1 product` / `1:1 clone` / `1:1 copy` / `1:1 replica` 等明示按正品仿制的措辞」——属公开声明售卖仿品，即使品牌不在 877 库内也判高风险（判据见第 4.6 步与 `concealed_fake_sales_standard.md` 第二·五节 CF-G8）。
- **中风险**：未命中高风险品牌库，但触发 SOP 框架其它维度的风险信号。包括：
  - 文字商标变形词、碰瓷词（`nik` 蹭 Nike、`Bowstick` 蹭 Patchinko）
  - 通用词被用在品牌注册类目（Apple 卖电脑）
  - 未登记高风险品牌库的品牌 Logo / 立体商标 / 外观专利（JOF、AJ1 鞋型、AirPods 外观）
  - 未登记高风险品牌库的著作权 IP（Pokemon、Marvel、Supreme、Disney 衍生形象）
  - D1 图片规避手法（马赛克 / 涂抹 / 贴纸遮挡商标、线条图、白底型号词图）
  - D2 暗示售假关键词（`1:1` / `replica` / `aaa` / `clone` / `yupoo` / `putian` / `thai version` 等）
  - 配件类表述不合规（`canon battery` 缺主体）
  - 二手奢侈品风险
  - **隐性售假场景**（第 4.6 步命中）：去标仿版瓶型/盒型、批量货架陈列、整箱堆积、大量散样、手绘/渲染/截图替代实拍、品牌名压黑条、站外引流广告、`original`/`catalogs`/`contact us` 等暗示词——详见 [`concealed_fake_sales_standard.md`](concealed_fake_sales_standard.md)

#### 第 2 列「侵权内容」填写规范

每个单元格**强制采用两段式结构**，中间用 `<br>` 换行分隔：

```
**位置**：<侵权位置>
<br>
**依据**：<文本片段或图片>
```

**位置段**（第一行）：
- 必须从以下封闭枚举中取值（与 Step 1.4.5 全证据表的"信息类型"列严格对齐）：`商品标题` / `商品主图` / `商品属性` / `商品详情文字` / `商品详情图片` / `商品视频`
- 同一风险点出现在多个位置时用 ` / ` 拼接，例如 `商品主图 / 商品详情图片`
- 不得简写（不能写成 "标题"、"主图"、"SKU"），不得自创位置类别
````

- **B2B 豁免规则的边界严格遵守**：豁免**只对文本中"B2B 业务说明性片段"**生效（含 wholesale / custom / customize / OEM / ODM / MOQ / private label 等同义词的句段）；**所有图片侵权（A2 / A3 / B / C / D1）一律不豁免**；**D2 暗示售假关键词一律不豁免**；**直接使用他人品牌名作为商品身份描述一律不豁免**。**豁免预处理是内部判断步骤，最终报告中绝不出现任何与豁免相关的提示词、说明行或元信息**——豁免是否生效、豁免了多少段、哪些词被识别为业务用语，全部对用户隐藏，报告只展示最终判定结果。

## 关键实现细节

### 何时主动追问

- **阿里商品链接的 MCP 调用不成功**（`code != 200` / 网络失败 / 数据全空）→ 按 Step 1.0a「MCP 失败处理」回复失败话术，请用户稍后重试或改提供商品图片素材；**不**改用其它抓取方式。
- **图片清晰度极低**导致 `see_image` 完全无法识别 → 告诉用户"图片细节不足以判断，能否提供更高清的图或多角度图？"
- **入参完全模糊**（例如只发了一个商品类目"卖鞋的"）→ 追问"具体哪一款？方便贴一下链接、图片或标题吗？"

### 报告语气

- 务实直接，不"贩卖焦虑"。命中时直接说风险等级（高风险 / 中风险）和处置建议；不命中时也提醒"管控名单不是全集"。
- 不要在报告里说"我读了 Excel" 或"我调用了脚本"——这是实现细节。
- 用户语言不明显时默认中文。

### 执行时机的"快路径"

如果用户只贴了一段纯英文标题，且**字数 < 100**，可以省略写文件这一步，直接：

```bash
py "<skill_dir>/scripts/match_brands.py" --text "<标题原文>"
```

但凡涉及图片或长详情，按完整流程走。

## 数据更新

当用户提供新版 xlsx 时：

```bash
py "<skill_dir>/scripts/build_blacklist.py" "<xlsx路径>" "<skill_dir>/assets/brand_blacklist.csv"
```

脚本会重建 CSV，去重 + 过滤已停用品牌，匹配引擎自动用新数据。

## 已知边界

- **高风险品牌库覆盖**：877 个平台高风险品牌；Pokemon、Marvel、Supreme 等如果不在高风险品牌库内，匹配引擎不会报警，但第 4 步「全证据表逐行判定」的判定项 b（高风险库外 IP / 著作权）会主动作为"非高风险库品牌，但存在风险"识别出来。
- **中文品牌**：目前高风险品牌库中中文品牌较少（如"老干妈"、"茅台"）；如果用户主要做中国品牌相关商品，建议补充行业自查。
- **图片遮挡推测**：基于多模态模型的视觉推理，存在不确定性；置信度低的猜测仅供参考，不构成最终判断。
- **视频 / 直播内容**：本检测无法逐帧识别视频中的违规点；如商品包含视频或直播，需用户自行截图或提供关键帧。
- **商品信息来源（唯一 MCP）**：alibaba.com 商品链接的标题 / 图片 / 属性 / 详情**只能**通过官方 MCP `query_product_page_info` 获取——MCP 直接返回 description（含详情文字与详情图），不存在 PC 端 JS 异步加载漏抓问题。**严禁**用 web_fetch / probe 脚本 / browser 子代理抓阿里商品页；MCP 调用不成功时直接回失败话术、终止检测，无任何降级抓取。
- **店铺级内容（不获取、不检测）**：本检测仅覆盖商品详情页 listing 级（标题 / 属性 / 详情文字 / 商品图 / 详情图）。**店铺名、店铺头像、店铺主营信息、店铺装修首页（banner / 导航 / 装修组件）一律不获取、不检测、不进命中表**；即使用户上传店铺截图也不纳入命中表。这些店铺级位置的违规需用户自行核查。
- **评论区（不采集）**：MCP 不返回评论区数据，评论区买家图与文字**一律不采集、不检测**。
- **专利侵权**：本技能主要识别外观设计专利的明显近似；实用新型专利与发明专利的判断需要权利要求解释，建议咨询 IP 律师。
- **权利状态有效性**：本检测假设高风险品牌库中的品牌权利均处于有效状态；商家如对某品牌权利状态有疑问，请到 WIPO / EUIPO / USPTO 等官方网站核验。
